# GUI

A plan for graphical interfaces, tried out in `gui/` over the builtin `Window` of the library (The library of `doc/implementation-notes.md`). The ulang side is functional, in the architecture of Elm: a program is a model, a pure `update` of the model by an event, and a pure `view` of the model as a tree of widgets, which a loop in ulang compares with the tree before and turns into patches of the widgets on screen. Decisions that new work keeps: no callback of GTK runs ulang, its signals only queue events, which `window_next` gives, so no exception of ulang crosses a frame of GTK; `update` and `view` stay functions, and effects are data that `update` returns (item 4); the diff, its patches, and the skeletons are values of enumerable types, which lemmas and their tests reach (item 3), while the handlers are looked up in the current tree by the id of the widget that the event names.

## Try-out

- `gui/protocol.u`: kinds, properties, shapes, the skeletons `Node` and `Placed`, the patches `Op`, the events, `create` and `diff` by position, and the lines of both directions; `gui/widget.u`: the abstract `Widget[E]` and `Attr[E]`, their builders as in Elm, `map_events`, `skeleton`, `misplaced`, `handle`, and the finders `click` and `input` for tests; `gui/app.u`: `App`, `simulate`, and `gui_run`, which raises `GuiError` for a misplaced attribute.
- `gui/examples/`: `counter.u`, `todo.u` (an entry, checks, a filter, with checks reused by the diff when the filter hides a row), and `life.u` (a canvas with pointer events), each tested by `simulate`, `click`, and `input`.
- `out/ulang.sh run gui/examples/todo.u` runs one on the screen; `ULANG_WINDOW_SCRIPT=FILE` drives the window by the commands that `window_next` of `ulang/prelude/window.u` lists and writes shots as PNG, `xvfb-run -a` around it without a screen.
- Learned: the diff by position is enough for these examples, since the handlers are looked up in the current tree, so a reused widget gets the event of its new place; `expand` must grow along the axis of the box around it, else an entry in a row grows tall; the window only queues events, so a slow `update` loses nothing; `gtk_widget_activate` of a button emits `clicked` only after the animation of the press, so a script that clicks twice loses a click, and the runtime emits `clicked` itself; and a window that no `window_close` closes stays until the program ends, since its state is of malloc, which the collector does not finalize.

## Items

1. **The library has no package that a program imports explicitly**: every member of `ulang/prelude/` is imported by every module (`implicit_imports` of `ulang/syntax/syntax.u`), so `window.u` is seen everywhere, while `gui/` is a package of this project, and `import prelude` is rejected. Solution: either `window.u` stays a member of the library, or subdirectories of the library become packages of their own, imported by `import prelude.gui`, loaded from the directory that `os_library_dir` of `ulang/prelude/os.u` gives, never implicitly, with the parser accepting that prefix only for directories below the library (`import_package` of `ulang/parse/parse.u`), as the tester already loads `ulang/test/enumerate/` next to the library (`load_after_library` of `ulang/parse/parse.u`), and `gui/` moves there with the builtins of windows; its modules are `prelude.gui.gui` and so on, kept by their file names in C.
2. **The protocol is lines, and lacks widgets and events**: the builtins take and give lines of fields separated by tabs, so that the library has one type and five names and the runtime reads no datatype of `gui/`, and raise `OsError`. Open: whether the protocol stays lines, cheap to add to, or becomes datatypes of the builtin section, which the runtime reads by their tags and fields as it reads `IoMode`, with a `GuiError` of its own; a patch that moves a widget, `PMove(id, index)`; the widget `scroll(attrs, children)`, the attributes `on_key(f)` and `key(k)` of children (item 3), and the events of keys and of timers (item 4); consecutive inputs of one entry and pointer motions merged in the queue, so that a slow `view` does not fall behind. Grids, lists of many rows (`GtkListView`), menus, and dialogs later, each a function and a kind of the protocol.
3. **The diff has no keys and no proofs**: `diff` of `gui/protocol.u` matches children by position. Solution: keys of children (the attribute `key(k)`, as `Html.Keyed` of Elm) as a second step for lists that insert in the middle; and `realize(patches, screen)`, a pure model of what `window_apply` does to the tree of widgets, which is what the lemmas speak of:
   - `lemma diff_realizes(old: Placed, new: Node) := ensures realize(first(diff(old, new, fresh(old))), screen_of(old)) == screen_of(second(diff(…)))`, i.e. the screen after the patches is the new tree, and no patch names an id that the screen lacks.
   - `diff(p, skeleton_of(p))` is empty, so a `view` that gives the same tree touches no widget.
   - Their tests `l.lemma` enumerate small trees, which a `Node` of kinds and texts allows, and `check --prove` may prove them by induction on the tree; a gap is no reason to stop, the tests and examples carry the work meanwhile.
4. **The loop has no effects**: `gui_run` of `gui/app.u` repeats events, `update`, `view`, and `diff` until the window closes. Solution: effects as data, Elm's commands: `update` of an `App` with effects returns `(M, List[Effect[E]])`, with `Quit`, `Every(milliseconds, E)` (a timer of GLib, raising a tick), `ReadFile(path, Result -> E)`, and `WriteFile(path, text, E)`, which the loop performs between events, its `OsError` turned into an event, so a program reads and writes files without a procedure of its own; an `App` without effects is the case of an empty list, built by a function `simple(title, init, update, view)`.
5. **Scripted runs are not tested**: `simulate` tests programs without a screen, and `ULANG_WINDOW_SCRIPT` drives a window, but nothing runs the scripts. Solution: a target `make testgui` that runs the programs of `gui/` compiled under a script, under `xvfb-run` or a headless compositor, and reads back their shots, only after asking, as the other compiled tests are.
6. **Examples**: the list of tasks of `gui/examples/todo.u` with keyed children and `ReadFile` and `WriteFile`; the game of life with `Every`; and later a viewer of the outline of a ulang file by `refactor @outline`, a first tool of the language with a window. Each joins `examples/` with its tests by `simulate`, see `ideas/examples.md`.

## Steps

1. Item 1, where the package lives.
2. Item 3, keys, `realize`, and the lemmas, all pure, before any C.
3. Item 4, effects and timers, then item 2 for the widgets and events they need, in both backends and the interpreter, then `make testc` and `make testelf` after asking; then item 5 and the examples of item 6.
4. `doc/language.md` a section of programs with windows; this file deleted when the examples run.

## Open

- Whether `update` gets the effects in every `App`, Elm's choice, or only in a second constructor, as item 4 assumes, so that the first programs are shorter.
- Whether the queue of raw events should also be reachable without a window, so that `window_next` serves timers and sockets together, which Library 1, `io_poll`, would join.
- The names of the builders follow Elm, `text` among them, which a local `text` hides, a common name of locals, so that `text(s)` then calls the local; `HiddenLocal` does not catch it, since locals may hide declarations, so either the error of the call names the hidden function, or the builder is `label`.
- Capabilities (Later 1 and 4): opening a window is an effect that the signature of `gui_run` shows only by `GuiError`.
- A second backend for the same ulang code, e.g. a browser over `io_listen` of `ulang/prelude/io.u` that renders the patches as DOM, since the protocol does not depend on GTK.
