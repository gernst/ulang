# Build

1. **Building and testing are spread over the Makefile and the commands of `ulang.bin`**: compiled programs are linked by hand, with `-DULANG_LIB`, `-I ulang/runtime`, the runtime, `-lgmp`, and `-lgc`, also the binary of the tests of the project that `compile --tests` writes as C; and `project.u` declares only the directories that run compiled, without the programs of a project or where outputs go. Solution: `ulang.bin` as the one tool, as `cargo` is for Rust, which calls the C compiler itself, and a Makefile that only builds the seed.
   - Processes: builtin procedures of `os` that start a process with arguments and wait for its status, also several at once for parallel jobs, e.g. `os_spawn` and `os_wait`, in both backends, where the interpreter uses those of the host.
   - `ulang.bin build <file> [<entry>]` checks, compiles to C, and links a binary, all in `out/` of the project: the runtime as an object compiled once and kept, the C compiler from `CC` or `cc`, the flags and libraries in one place of the tool, and the paths of the library and the runtime fixed when the tool is built, as `ULANG_LIB` is now. A build is redone when a hash of its inputs differs, the loaded modules, the runtime, the flags, and the tool, recorded next to its outputs, not by times.
   - `ulang.bin test --compiled [<path>[:<name>] …]` builds the binary of the tests of the project, as `make testc` does now by `compile --tests` and `cc`, when it is stale, and runs it with the same arguments, so that the Makefile no longer links it.
   - `--list` of `test` and of the binary of the tests, which prints the tests that the arguments select, as `file.u:name`, one per line, in the order in which they run, without running them, for the VS Code extension and for scripts.
   - Project: `Project` of `ulang/prelude/os.u`, which the function `project` of `project.u` gives and the driver reads with the interpreter, as Zig reads `build.zig`, so that the metadata stays in ulang files, typed by the checker, grows by the programs as values, e.g. `Program("ulang", "ulang/ulang.u", "main")`, and the directories of tests; `ulang.bin build` and `ulang.bin test` without paths take them from it.
   - The Makefile keeps only the seed, `bootstrap/ulang.bin` from `bootstrap/ulang.c`, and targets that call `bootstrap/ulang.bin build` and the tool, while the check of the fixed point becomes `ulang.bin selfcompile`, which compiles the compiler twice and installs the seed as `make selfcompile` does now.
   - Later: dependencies of a project, by path and then by the URL and commit of a repository, declared in `project.u`, fetched into a cache outside the project, with a lock file of their hashes, and imported by paths whose first segment is the name that `project.u` gives them, as Go's module paths. Compiler 2 leaves the C compiler only for the runtime, compiled once, and as the driver of `as` and the linker.
   - Steps: the procedures of processes; `build` of one file; `test --compiled`; the programs in the project file; the Makefile reduced to the seed; then dependencies.
2. **Every compiled program contains the C of all the packages it loads**, which `cc` parses again for each program, although it drops what nothing reaches, since the generated C is `static` except what `ulang/runtime/ulang.h` declares extern (`runtime_referenced` of `ulang/compile/lower.u`, `Linkage` of `ulang/compile/c.u`): the library was about 106 KB of the 123 KB of C of a small test of strings, about 70 ms of its 175 ms of `cc -O2`, the compiler's `cc -O2` takes about 11 s, and the C of the library and the compiler is parsed again for the binary of the tests of the project after any change. Solution: packages compiled separately, each once, into a static archive, which programs link, with the library as the package `prelude`, a case of the same mechanism, not a special one; no shared libraries, which would need position-independent code, rpaths, and versions of their own, for no gain in binaries that tests throw away. The plan in detail is `ideas/archives.md`.
   - What makes it possible: every value is a `u_value`, without specialization by type, so one compiled `list.foldr` serves all callers; checked programs carry only resolved names, `Name(Some(m), …)`, which `mangle` and `c_text` of `ulang/compile/lower.u` make stable C names; and orders, equality, and show are reached through the descriptors `t_…` of the types, not called by the users of a type.
   - A package: `compile --package <dir> <out>` writes the C of its members, without their tests, with the exported declarations and the descriptors of exported types `extern`, the private declarations with hidden visibility, so that the tests of a member, which see its private declarations, can link them, and `static` only what nothing outside the C file reaches. With it go what each program now gets for every module it loads: the functions without parameters as globals computed at the first use, the accessors and updaters of fields, and the wrappers `wp_` of its procedures; the formats `u_text_*` go into the runtime or the archive of `prelude`. One C file and object per member; each unit declares what it references of other modules itself, from `Defs`, without generated headers. Each function in a section of its own, `-ffunction-sections`, so that the linker, by `--gc-sections`, keeps only what is reached, which replaces `runtime_referenced`.
   - A program: `compile` emits only the modules of the program, or for the tests of a member that member, and links their archives, `out/lib/<package>.a`, with the runtime in the archive of `prelude`; the front end still parses and checks the packages it loads, which takes tens of milliseconds, and a cache of their `Sig` waits until that matters.
   - Staleness: each archive is rebuilt when a hash of its inputs differs, the sources of its members, the stamps of the packages it imports, the runtime, the flags, and the tool, as in Build 1, and the hash is a symbol of the archive, which each unit that uses the package references, so that a program linked with an archive of another build fails to link, not at run time.
   - Kept: the whole-program translation, the default of `compile`, for the seed, `bootstrap/ulang.c`, which stays one self-contained C file, and for `make selfcompile`, which compares such files.
   - Lost: `cc` no longer inlines functions of other packages, such as those of `option`, into their users; inlining at the level of ulang (Compiler 3) gets it back, since the front end sees the sources, and `-flto` meanwhile, at the cost of time.
   - Clash: a project with a directory `prelude/` at its root, which already clashes with the library in C, gets duplicate symbols when linking, which `CLAUDE.md` states.
   - Backends: the plan is of C, whose `cc` it saves most, while `ulang/compile/x86.u` has its own `wrappers`, `data_decls`, and `texts`, and `cc` of the `.s` of the suite takes about 0.9 s; whether the assembly backend compiles separately too is open.
   - Steps: the archive of `prelude`, linked by the binary of the tests; then any package, and the tests of `ulang/` against the archive of `ulang`; then `ulang.bin build` (item 1) building and caching the archives of the packages a program loads.
3. **The seed lags the sources**, which `CLAUDE.md` says only for keywords: `make` translates the sources and the library with the seed, so `ulang/` and `ulang/prelude/` can use a new syntax only after `make selfcompile` has replaced the seed, e.g. a doc before a statement or an `example` in `list.u` failed `make` until then; `make selfcompile` depends on `out/ulang.bin`, which `make` then wants to rebuild with the old seed, so the way through is `make -o out/ulang.c -o out/ulang.bin selfcompile`; a rule of the checker that the seed's checker breaks on the new sources, as the exact comparison of raises, took a copy of the sources without the annotations, built by the old seed, whose C became the seed; and two branches that each teach the seed a syntax that the library uses, `raises` and `example`, could be merged by neither seed, only by `make` with the lines of one taken out, then `selfcompile` with them back. `make bootstrap` does not help, since the interpreter of the seed parses the same sources. Solution: a target for the first case, which takes the current binary as the new stage, `CLAUDE.md` states that a new syntax reaches `ulang/` and the library one commit after the one that teaches it, with the seed replaced in between, and branches that teach the seed merge one at a time, each with its new seed.
