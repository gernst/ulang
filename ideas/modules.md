# Modules

1. **`os` is a member of the library**, so every module sees the procedures of the system without importing them. Solution: `os` as a package of its own, imported by what uses it, after an experiment that shows which uses become ambiguous.
2. **Names cannot be qualified by their package**, so two imported packages that declare a type of the same name make every use of it `Ambiguous` (`normalize` of `ulang/check/check.u`), and a clash that overloading by type cannot decide has no way around it but renaming. For example, `ulang/prove/` could import `ulang/syntax` only after renaming its `Expr` and `Branch` to `Term` and `TermBranch` of `ulang/prove/syntax.u`, and it still shares the constructors `EApp`, `ELam`, `EIte`, and `EMatch`, told apart by type; and `Gen` of `ulang/syntax/syntax.u` cannot be named in `ulang/compile/compile.u`, whose own `Gen` hides it, while its constructors `GVal` and the like stay visible, so code there matches the shape of a generator instead of taking a `Gen`. The checker already resolves qualified uses: `visible_names` and `overloads` take `Name(Some(m), base)` as exactly the declaration of module `m`. What is missing is syntax, and a meaning of the qualifier as a package. Solution:
   - **Qualifiers**: the last name of the path of each imported package, `syntax` for `import "ulang/syntax"` and `nested` for `import "ulang/test/modules/paths/nested"`, written `q.x`. Two imports with the same last name are a parse error until there is a need for `import "…" as q`. A package whose last name is a keyword cannot be qualified. Possibly also the own package and `prelude`.
   - **Where**: in types, `syntax.Expr`, and in patterns, `case syntax.EApp(f, args) =>`, where `.` does not occur now, so the parser builds the qualified name directly. In expressions, `syntax.size(xs)` parses as the field access `EField(EVar(syntax), size)`, which the checker reads as a qualified name when its base is a qualifier. That needs no state of imports in the parser, and is unambiguous since a formal, local, or pattern variable of the name of a qualifier is an error, as `HiddenLocal` is.
   - **Meaning**: a qualified use has as its candidates the exported declarations of the members of that package, among which overloading by type still decides. It never reaches private declarations, unlike the exact `Name(Some(m), …)` of checked code, which `overloads` takes without `is_visible`.
   - **Representation**: the parsed name needs a mark that it names a package, not a module. The ids can coincide: the program `ulang/test/modules/paths.u` has the module id `ulang/test/modules/paths` and imports the package `"ulang/test/modules/paths"`. Options are a field of `Name`, or a constructor of uses that the checker replaces; not an encoding in the string (Code 3). `format` prints the qualifier as written.
   - **Nearness for types**, to decide with it: a type of the module hides those of other modules already, and the library's are hidden by any module's. If the members of the own package also hid the types of imported packages, `ulang/prove/simp.u` would keep writing `Expr` for its own, and only `ulang/prove/translate.u` would write `syntax.Expr`, instead of every file of `ulang/prove/` qualifying both.
   - Then `CLAUDE.md`, under Modules and Overloading, where "the parser builds no qualified names", and the highlighting of the VS Code extension; tests of qualified types, patterns, and calls, of a qualifier hidden by a local, of a clash of qualifiers, and of a qualified private name.
3. **The structure of packages is to be discussed again**, also from its costs to a writer of programs: a broken scratch file beside a program made `check ok.u` print 13 errors of the other file as `ImportError` and fail; `format` of a copy of a file outside its directory fails with `unknown package`, and of a file beside a broken sibling with the `ImportError` of the sibling, since it loads the package, so a tool that formats candidate texts must do so in place (the mail client of 15 November 2026): a package is a directory whose members are all its `.u` files but `project.u` (`package_files` of `ulang/parse/parse.u`), imports are paths from the root of the project, and `project.u` at the root declares only the directories that run compiled. Preferred: one file *inside* each package that declares it, as `prelude.u` marks the library now, with all resolutions of its members, of imports and of paths, relative to that file; and one file of the project at the *top level*, which also holds its metadata, the programs and the directories of tests of Build 1, its dependencies, and the like. To decide with item 2 and Build 1, whose project file it is: what the file of a package declares, its members or only its presence; whether an import names a package by its path from the root or by its declared name. Decided: a package is exactly its directory, spanning no subdirectories (`CLAUDE.md`, Modules). The library would follow the same rule; it is already its directory, the one that `os_library_dir` gives, as a package of a project is.
4. **A run over many files loads per unit**, a package of its targets: each unit parses and checks its own package, joins the signatures of the packages checked before, and loads the tester, so that the driver threads a cache through the units, `Cache` of `ulang/ulang.u` by `load_file`, of the packages parsed (`parse_file_loaded` of `ulang/parse/parse.u`) and checked without errors (`check_cached` of `ulang/check/check.u`), which took `check` of the project from 22.8 s to 9.9 s, and `compile_tests` takes each module from the unit that it is a member of. Solution, a simplification, and a speedup only if a profile shows one: one source for all the targets of a run, each package once, in load order, checked once, from which the driver reports, runs the tests, proves, or lints per package, since the checked program keeps every command with its module, and `Cache` goes.
   - Before starting: a gprof profile of the compiled `check` of the project, to tell whether the time left is in the units' own packages, which one source does not save, or in the joins of signatures and the loads of the tester, which it does.
   - Tests: a package keeps its tests if it is a target, not only if it is the package of the main file (`without_tests_of` of `ulang/parse/parse.u`); importers never see tests, so this is harmless.
   - `Source` and `Prog` have one `main`, the module of the loaded file, which for a run of many targets is none, so the driver takes the tests and the entry by the modules of the targets, as `check_unit` and `compile_tests` of `ulang/ulang.u` do now by the files of a unit.
   - Errors: a unit fails only by the errors of its own package and of those it imports, so the diagnostics of the one source are filtered per package by the packages it sees (`seen_modules` of `ulang/syntax/syntax.u`), where per unit the source holds no others.
   - `units` of `ulang/check/check.u` and `module_package` of `ulang/parse/parse.u` take the package of a module by its name, `module_dir` of `ulang/syntax/syntax.u`, as `check_source` of `ulang/check/check.u` does, instead of finding it in `Source.packages`, without their cases of a module of no package, which only the fixtures of tests make; their modules then take names with directories, one per package: those of `ulang/syntax/fixtures.u`, `bags` of `ulang/check/check.u`, `parse_text_recovering` of `ulang/parse/parse.u`, and the source that the tests of `ulang/check/hints.u` build.
