# Testing

1. **The tests with formals start from the smallest values only**: they run on the enumerated values of their formals (`enumerated_tests` of `ulang/test/generate.u`), so the calls that the examples of the functions under test document are not among their cases, and they run after the other tests of their module, not in the order of the source. Solution: the examples of the functions that the test calls as its first cases, and the runners in the order of the source. They give the evidence "tested" of Verification 2.
2. **The tests of lemmas are limited**: a counterexample is a string in quotes inside `uncaught exception Falsified("…")`, with the escapes of the `Str` formals; type parameters are only `Int`; the depth is chosen once, so a lemma over two lists sees lists of at most 2 elements, and one whose assumptions small values do not meet, `requires n > 100`, is `Vacuous`; and abstract types are not enumerated. Solution: the runners print `Falsified` of `ulang/test/enumerate/enumerate.u` as `falsified for x = 1, …`, in both backends, which takes a design of its own: the runners see only the text of the uncaught value, a builtin procedure that fails a test with a message belongs to the library, whose builtin sections alone declare them, the C runtime does not know the descriptors of the types of the enumeration, which programs without tests lack, and a `show` of `TestFailure` that printed the text would not parse back; abstract types enumerated by their exported constructions, from the examples of their functions or a declared enumeration; and random values beyond the depth, by a seed in the name of the test, when a lemma needs larger cases.
3. **Examples are seen only in the source**: `sig`, planned in Diagnostics 3, and the hover of `ulang.sh hints` do not show them, the `▶ Run` links of the extension do not reach them, and a failure reads `assertion failed: 3 != 6` instead of `example 1 of gcd failed: gcd(12, 18) gave 3, expected 6`. Solution: `sig` and the hover print the examples below the signature, the extension shows `▶ Run` above each, and the test of an example asserts by a statement that knows its call.
5. **A case cannot catch an error that the tree of the checked program loses**: `check_text` of `ulang/test/cases/cases.u` raises the first error of the list that the checker builds, not of `diagnostics` of the checked program, which is what `check` prints, so a case of a lost error reads `diagnostics` of `checked_text` by hand, as `errors_of_forms` of `ulang/test/errors/types.u` does. But a `Diagnostic` of `ulang/syntax/error.u` does not hold the `TypeError` that the cases match on, about 180 patterns `Located(…)`, also by its structure, as `Mismatch(_, _, "an element of List")`. Solution: decide between an exception over a `Diagnostic`, which changes every such case to a code and a position, and `check_text` that keeps raising the first `TypeError` but fails with an internal error unless the first of the diagnostics has its position and code, which catches a lost error without touching the cases.
6. **The tests of lemmas over functions that do not terminate grow memory without bound** under the `ulimit -s unlimited` of `ulang.sh`, which once killed a session, so samples run under `ulimit -v` and `timeout` by hand. `check --test --timeout <seconds>` limits the time of each test in the interpreter, but not its memory, which a deep recursion fills before the limit, and the binaries of `compile --tests` take no limit. Solution: a limit of memory, by the maximal heap of the collector (`GC_set_max_heap_size`) and the depth of the stack, whose failure names the test, and both limits in the runner of the compiled tests (`u_run_tests` of `ulang/runtime/ulang.c`).
7. **Each file of a unit expands the whole program again for its tests**: `test_module` of `ulang/test/runner.u` builds the state of the interpreter by `load(q)` of `ulang/run/run.u`, `defs_of(expanded(q))`, for each file of a unit, over all commands of the checked program, those of the library and the imports included, which no run keeps, so the files of `ulang/check/` expand most of the compiler once each; `prove_module` likewise translates the program by `translate(q, m)` for each file with lemmas. Of the 92 s of a `make test` at a load of 3 (16 November 2026), about 37 s went before the first test of each file, the load of its unit and of its first test together, not measured apart. Solution: one `load(q)` and one translation per unit, shared by its files, which `check_unit` of `ulang/ulang.u` would pass to `test_module` and `prove_module`, and then a cache of the expanded commands of each package that checks without errors, as `Checks` of `ulang/check/check.u` keeps the checked ones.
8. **The functions without parameters are computed again in each test**: `test_message` of `ulang/test/runner.u` runs each test with a cache of the values of such functions that starts empty, `var cache: Map[Name, Val] := empty()`, so a table such as `builtin_names` of `ulang/run/run.u` or the keywords of the lexer is computed once per test that reaches it instead of once per run. Solution: one cache per `test_module`, passed from test to test, which holds since such a function has no effects and its value depends on nothing that a test changes; measure the share first, by gprof of a `check --test` of `ulang/check/check.u`.
9. **The walk of `make test` loads unit by unit**: each unit is a checked program of its own, around its main package, since imports drop the tests of the packages they load, the tests of lemmas are generated only for the main package (`generate` in `check_source` of `ulang/check/check.u`), and the errors are placed relative to `source.main`, so the parse and the check of imports are shared through the caches of `visit_units` of `ulang/ulang.u`, while everything that items 7 and 8 name is repeated per unit or per file. Solution: the walk of the whole project checks one program of all its packages, each with its tests and the generated ones, and runs the tests and proofs of every module from it, with the errors placed per file; weigh it against items 7 and 8, which may take most of the gain for less.
