The sections are in the order of their value for the agents that write ulang, which have almost no ulang in their training data and learn the language from its documentation and its errors, while its design, one way of each construct, a canonical format, exhaustive matches, pure functions, and atomic effects, already suits them: so the feedback of a run comes first, all errors at once (Diagnostics 1), the fix (Diagnostics 2), and the resolution of names (Diagnostics 3), then the examples of signatures (Testing 2) and a reference of the language (Documentation 1).

## Diagnostics and refactorings

1. **The parser reports only the first error of a command, and errors are lines of text**, which tools and agents parse, and the VS Code extension by a regular expression, while the parser resumes at the next command (`ParseErrors` and `skip_command` of `ulang/parse/parse.u`) and the checker reports all type errors of the first package that has some (`check_all` of `ulang/check/check.u`). Solution: the parser also resumes at the next statement and at the next argument, keeping what does not parse as an `AUnparsed` of `ulang/syntax/syntax.u`, whose text needs the offsets of the tokens, and checks the commands that parse; and the errors printed as one JSON object per line, the fields of `Diagnostic` of `ulang/syntax/error.u`, read primarily by agents and the extension, and descriptive enough for people, without a text form, where the exit status tells parse, type, test, and internal errors apart (`diagnostics.md`, steps 8 and 9).
2. **Errors do not suggest their fix** where the checker or the parser knows it, and the habits of other languages, which agents bring along, get only the token that was expected: `x := e` as a statement is `end expected but x found`, `[1, 2]` is `expression expected but [ found`, `return 1` and a call without `call` are `declaration expected`, `elif` is `end expected but elif found`, `assign y += 1` is `:= expected but += found`, the missing `end` of an `if` after `else` is found only at the end of the input, and `s + "x"` of strings is `cannot unify Int and Str`. Solution: suggested edits as refactorings (item 4), e.g. the missing cases of a match, or a qualified name for an ambiguous use, listed with the diagnostic and carried out by `--apply`; and hints of the parser and the checker for these habits, which `CLAUDE.md`, Writing ulang, lists, each a message that names the form to write, `assign x := e`, `List(1, 2)`, `call p(…)`, an `out` formal, `else if c then … end` with its own `end`, `assign y := y + 1`, and `++` of strings, the `end` reported at the `if` it closes by the indentation, each with a case in `ulang/test/errors/`.
3. **The resolution of names is invisible**, and finding the uses of a declaration needs reading, since `size` in a file that imports `set` and `map` may be any of three. Solution: the checker records, for each use that the parser places, the qualified name it resolved to and its type, before it drops the positions; then `ulang.bin resolve <file> <L.C>`, the qualified name, type, and declaration of the use there, also as hover in the VS Code extension; `ulang.bin refs` of a use or of `module.name/arity`, all its uses in the files that import it; `ulang.bin sig <module>`, the exported signatures without bodies; and `check` of several files or a directory in one process.
4. **No refactorings**, so renaming a declaration means finding its uses by hand. Solution: refactorings as changes of the parsed tree, printed by `format_program`, which keeps docs since they are syntax: refused unless the file is formatted, which `check` ensures; checked again after; and refused if any other use resolves differently from before, which makes them safe under overloading without reasoning about it. They print a diff, or write the files with `--apply`. In order: rename, filling in the missing cases of a match, adding a field to a constructor with its constructions and patterns, and changing a signature with its calls; not extracting or inlining, which edits of the text do well enough.
5. **Code that could be simpler is only found by reading it**, e.g. `List(for e in List(for x in m) …)` instead of `for k => v in m`, the same projection `List(for x in xs yield x.name)` repeated, a hand-written `match` on `get(…)` that is `value_or`, or a collecting loop `xs := xs ++ List(v)` instead of a `Buffer`. Solution: rewrites on the checked syntax tree, each from a pattern to a simpler term that keeps the meaning, which `ulang.bin check --lint` reports as warnings with the position and the replacement, opt-in, since warnings that a run always prints are noise that agents either chase or learn to ignore, which `--apply` carries out as a refactoring, and which the compiler may apply as the optimizations of Compiler 3; each rewrite has a test of the source that triggers it and of the result.

## Testing

1. **Properties are only tested on the examples written by hand**, and the formals of tests are reserved but rejected. Solution: tests with formals, `test append_size(xs: List[Int], ys: List[Int]) := assert …`, which the runner calls on generated values of the types of the formals, deterministically, and which report the values of a failure. They give the evidence "tested" of Verification 2.
2. **What a function does is seen only from its body or from tests elsewhere**: a signature gives the types, a doc gives prose that nothing checks and that goes stale, and the tests of a function sit apart from it, often in another file, private to their module, so neither a reader of the `export` section nor an importer, nor an agent that reads a signature or `ulang.bin sig` (Diagnostics 3), sees a concrete call with its result. Solution: examples as part of a signature, checked and run, documentation that cannot go stale:
   - **Syntax**: clauses `example` between the signature and `:=`, or after a signature without body in `export`, one per line, where `example` becomes a keyword:
     - of a function, an equation of a call and its result, `example gcd(12, 18) == 6`, or a call that raises, `example chr(-1) raises NoCharacter(-1)`;
     - of a procedure, a call whose arguments for the outs are the expected values, `example divmod(in 7, 2, out 3, 1)`, and a ref given as before and after, `example push(in 3, ref List(1) => List(3, 1))`, or `raises` as for functions.
   - **Where**: on the first occurrence of a signature, in `export` for the exported ones, which the definition in `implementation` does not repeat, as it repeats the signature, so an importer sees them; on the definition for private ones. An example of an export section names only what the export sees, the exports of the module and its imports, so it is a call that an importer could write; so an example of an abstract type builds its values by the exported functions, `example size(insert(1, empty())) == 1`.
   - **Checking**: an example is a closed expression of type `Bool`, without locals, whose call names the declaration it belongs to, resolved by the overloading of the module, so `example size(List(1)) == 1` of `set.size` is an error. It is checked with the module after its declarations, and respects the `requires` of the function (Verification 1), which an example outside its domain violates.
   - **Running**: `ulang.bin test` runs the examples of a file as tests of their own, named `name.example.N` with `N` from 1 in the order of the source, in both backends, also by `make testc`, and a failure shows both sides, `example 1 of gcd failed: gcd(12, 18) gave 3, expected 6`; examples of the library run with the tests of `ulang/prelude/`. `ulang.bin sig`, the hover of the VS Code extension, and the `▶ Run` links show them.
   - **Uses**: tests of one call each, such as `test paths()` of `ulang/prelude/os.u` for `os_dirname`, become examples of their functions; the examples are the first values that the generated tests of item 1 try; and examples are obligations that the prover checks against the contracts of Verification 1 by evaluation, a cheap check that a contract is not false.
   - **Not**: examples in docs, as Python's doctests and Rust's examples in `///` are, since docs are not checked and their text would need a parser of its own; and examples with free variables, which are properties, item 1.
   - Then a rule of style in `CLAUDE.md`, that an exported function whose name and types leave its meaning open has an example, e.g. of the order of its arguments, and `format` printing the clauses.

## Checker

1. **A raise cannot become a value**, so code that collects an error catches each kind into an out, as `check_file` of `ulang/ulang.u` does with the message of each phase, and the long `raises` of the helpers of `ulang/test/cases/cases.u` list every phase. Solution: a statement that gives an `Option` of the exception of a call, or a `try` with a result, and the exceptions of the phases as one datatype of `ulang/syntax/error.u`.
2. **Termination is a style rule only**, so the split between functions and procedures guarantees nothing, and unfolding a function that does not terminate can prove false. Solution: the prover proves the termination of the recursive functions that the lemmas of a module reach, by structural recursion or a lexicographic order of measures from the guards, each call an obligation of the simplifier, and uses the definitions of only those as rewrite rules, while `prove` and `test` report a termination error at a call that does not decrease; the checker stays out of it, `decreases` after `:=` is the fallback measure, and a check of the repository lists the functions of `ulang/` whose termination is not proven (`prover.md`, section 4).
3. **Unused imports are accepted silently**, so which packages a member needs is found only by removing each import in turn and checking, as when `ulang/` was split into packages, and a scan of exported names over the sources overstates the dependencies by words in docs and names that several modules declare. Solution: the checker rejects an import of a package of which the module uses nothing, at the position of the import, as `UnusedImport`.

## Syntax

1. **Folds cannot stop early, and the bounded quantifiers are missing**: `and` and `or` short-circuit in both backends, which stays, but a fold always walks its whole container, so `exists` and `forall` of the containers skip `p` once decided but still visit every element, and a search cannot end at its first hit; and `exists` and `forall` clash with the quantifiers of specifications (`prove.md`, open point 15). Solution: folds that take a test of the accumulator, after which they stop, `foldl(c, acc, stop, f)`, by which `exists` and `forall` stop at the first decision. Deferred, not convinced yet, since each is one more way to write a loop: bounded quantifiers `forall x in c => e` and `exists x in c if q => e` with the generators of the forms, where the unbounded `forall x: T => e` occurs only in specifications, which read the bounded ones as `forall x => contains(x, c) ==> e`, which translate to the stopping folds. The functions `exists` and `forall` of the containers stay until then.
2. **Errors show pattern aliases expanded**: `NotExhaustive` and `Unreachable` print the constructors that an alias stands for, e.g. `missing Some(false)` or `unreachable case Some(true)` where the case is written `Yes()`. Solution: fold a witness or a case back into the aliases whose stored patterns match it (`PatAlias` of `ulang/check/sig.u`) before printing, preferring the alias that covers most.
3. **The printer never breaks a chain of `++`**, however long, as `description` of `ulang/ulang.u` shows, while a `List(…)` wider than 80 characters gets one element per line, so long texts are written as lists of lines, as the cases of `ulang/test/errors/` are. Solution: a chain of an infix operator wider than 80 characters has one operand per line, each after the operator, at the indentation of the first operand.
4. **Checked lambdas have patterns as formals whose type does not say that they are variables**: `ELam(formals: List[At[Pat]], body)` of `ulang/syntax/syntax.u` is shared by the source and the checked program, where `lambda_match` of `ulang/check/check.u` leaves only variables, so the backends read them by `pattern_vars` or `lambda_vars` at every evaluation of a lambda, and the fusion of folds in `ulang/compile/compile.u` matches `AOk(_, PVar(x))`, an invariant that the type does not enforce. Solution: a type of checked programs of their own, or a checked lambda `ELam` of variables beside a source form of patterns, decided together with the record of resolutions of Diagnostics 3, which also separates what the checker gives from what the parser reads.

## Modules

1. **`os` is a member of the library**, so every module sees the procedures of the system without importing them. Solution: `os` as a package of its own, imported by what uses it, after an experiment that shows which uses become ambiguous.
2. **Names cannot be qualified by their package**, so two imported packages that declare a type of the same name make every use of it `Ambiguous` (`normalize` of `ulang/check/check.u`), and a clash that overloading by type cannot decide has no way around it but renaming. For example, `ulang/prove/` cannot import `ulang/syntax` without renaming its `Expr`, `Type`, `Name`, `Var`, `Pat`, and `Branch`, and maybe its constructors `EApp`, `ELam`, `EIte`, `EMatch`, and `ERaise` (`prove.md`, the plan). The checker already resolves qualified uses: `visible_names` and `overloads` take `Name(Some(m), base)` as exactly the declaration of module `m`. What is missing is syntax, and a meaning of the qualifier as a package. Solution:
   - **Qualifiers**: the last name of the path of each imported package, `syntax` for `import "ulang/syntax"` and `nested` for `import "ulang/test/modules/paths/nested"`, written `q.x`. Two imports with the same last name are a parse error until there is a need for `import "…" as q`. A package whose last name is a keyword cannot be qualified. Possibly also the own package and `prelude`.
   - **Where**: in types, `syntax.Expr`, and in patterns, `case syntax.EApp(f, args) =>`, where `.` does not occur now, so the parser builds the qualified name directly. In expressions, `syntax.size(xs)` parses as the field access `EField(EVar(syntax), size)`, which the checker reads as a qualified name when its base is a qualifier. That needs no state of imports in the parser, and is unambiguous since a formal, local, or pattern variable of the name of a qualifier is an error, as `HiddenLocal` is.
   - **Meaning**: a qualified use has as its candidates the exported declarations of the members of that package, among which overloading by type still decides. It never reaches private declarations, unlike the exact `Name(Some(m), …)` of checked code, which `overloads` takes without `is_visible`.
   - **Representation**: the parsed name needs a mark that it names a package, not a module. The ids can coincide: the program `ulang/test/modules/paths.u` has the module id `ulang/test/modules/paths` and imports the package `"ulang/test/modules/paths"`. Options are a field of `Name`, or a constructor of uses that the checker replaces; not an encoding in the string (Code 2). `format` prints the qualifier as written.
   - **Nearness for types**, to decide with it: a type of the module hides those of other modules already, and the library's are hidden by any module's. If the members of the own package also hid the types of imported packages, `ulang/prove/simp.u` would keep writing `Expr` for its own, and only `ulang/prove/translate.u` would write `syntax.Expr`, instead of every file of `ulang/prove/` qualifying both.
   - Then `CLAUDE.md`, under Modules and Overloading, where "the parser builds no qualified names", and the highlighting of the VS Code extension; tests of qualified types, patterns, and calls, of a qualifier hidden by a local, of a clash of qualifiers, and of a qualified private name.

## Library

1. **No binary data**: strings are code points, and the procedures of `os` read and write UTF-8 only, so a file that is not UTF-8 cannot be read. Solution: a type `Byte` with `Array[Byte]`, and procedures of `os` that read and write bytes, with explicit encodings between them and strings.

## Build

1. **Building and testing are spread over the Makefile and the commands of `ulang.bin`**: compiled programs are linked by hand, with `-DULANG_LIB`, `-I ulang/runtime`, the runtime, `-lgmp`, and `-lgc`, also the binary of the tests of the project that `compile --tests` writes as C; and `project.u` declares only the directories that run compiled, without the programs of a project or where outputs go. Solution: `ulang.bin` as the one tool, as `cargo` is for Rust, which calls the C compiler itself, and a Makefile that only builds the seed.
   - Processes: builtin procedures of `os` that start a process with arguments and wait for its status, also several at once for parallel jobs, e.g. `os_spawn` and `os_wait`, in both backends, where the interpreter uses those of the host.
   - `ulang.bin build <file> [<entry>]` checks, compiles to C, and links a binary, all in `out/` of the project: the runtime as an object compiled once and kept, the C compiler from `CC` or `cc`, the flags and libraries in one place of the tool, and the paths of the library and the runtime fixed when the tool is built, as `ULANG_LIB` is now. A build is redone when a hash of its inputs differs, the loaded modules, the runtime, the flags, and the tool, recorded next to its outputs, not by times.
   - `ulang.bin test --compiled [<path>[:<name>] …]` builds the binary of the tests of the project, as `make testc` does now by `compile --tests` and `cc`, when it is stale, and runs it with the same arguments, so that the Makefile no longer links it.
   - `--list` of `test` and of the binary of the tests, which prints the tests that the arguments select, as `file.u:name`, one per line, in the order in which they run, without running them, for the VS Code extension and for scripts.
   - Project: `Project` of `ulang/prelude/os.u`, which the function `project` of `project.u` gives and the driver reads with the interpreter, as Zig reads `build.zig`, so that the metadata stays in ulang files, typed by the checker, grows by the programs as values, e.g. `Program("ulang", "ulang/ulang.u", "main")`, and the directories of tests; `ulang.bin build` and `ulang.bin test` without paths take them from it.
   - The Makefile keeps only the seed, `bootstrap/ulang.bin` from `bootstrap/ulang.c`, and targets that call `bootstrap/ulang.bin build` and the tool, while the check of the fixed point becomes `ulang.bin selfcompile`, which compiles the compiler twice and installs the seed as `make selfcompile` does now.
   - Later: dependencies of a project, by path and then by the URL and commit of a repository, declared in `project.u`, fetched into a cache outside the project, with a lock file of their hashes, and imported by paths whose first segment is the name that `project.u` gives them, as Go's module paths. Compiler 2 would remove the C compiler from all of this.
   - Steps: the procedures of processes; `build` of one file; `test --compiled`; the programs in the project file; the Makefile reduced to the seed; then dependencies.
2. **Every compiled program contains the C of all the packages it loads**, which `cc` parses again for each program, although it drops what nothing reaches, since the generated C is `static` except what `ulang/runtime/ulang.h` declares extern (`runtime_referenced` of `ulang/compile/compile.u`, `Linkage` of `ulang/compile/c.u`): the library was about 106 KB of the 123 KB of C of a small test of strings, about 70 ms of its 175 ms of `cc -O2`, the compiler's `cc -O2` takes 10 s, and the C of the library and the compiler is parsed again for the binary of the tests of the project after any change. Solution: packages compiled separately, each once, into a static archive, which programs link, with the library as the package `prelude`, a case of the same mechanism, not a special one; no shared libraries, which would need position-independent code, rpaths, and versions of their own, for no gain in binaries that tests throw away. The plan in detail is `archives.md`.
   - What makes it possible: every value is a `u_value`, without specialization by type, so one compiled `list.foldr` serves all callers; checked programs carry only resolved names, `Name(Some(m), …)`, which `mangle` and `c_text` of `ulang/compile/compile.u` make stable C names; and orders, equality, and show are reached through the descriptors `t_…` of the types, not called by the users of a type.
   - A package: `compile --package <dir> <out>` writes the C of its members, without their tests, with the exported declarations and the descriptors of exported types `extern`, the private declarations with hidden visibility, so that the tests of a member, which see its private declarations, can link them, and `static` only what nothing outside the C file reaches. With it go what each program now gets for every module it loads: the functions without parameters as globals computed at the first use, the accessors and updaters of fields, and the wrappers `wp_` of its procedures; the formats `u_text_*` go into the runtime or the archive of `prelude`. One C file and object per member; each unit declares what it references of other modules itself, from `Defs`, without generated headers. Each function in a section of its own, `-ffunction-sections`, so that the linker, by `--gc-sections`, keeps only what is reached, which replaces `runtime_referenced`.
   - A program: `compile` emits only the modules of the program, or for the tests of a member that member, and links their archives, `out/lib/<package>.a`, with the runtime in the archive of `prelude`; the front end still parses and checks the packages it loads, which takes tens of milliseconds, and a cache of their `Sig` waits until that matters.
   - Staleness: each archive is rebuilt when a hash of its inputs differs, the sources of its members, the stamps of the packages it imports, the runtime, the flags, and the tool, as in Build 1, and the hash is a symbol of the archive, which each unit that uses the package references, so that a program linked with an archive of another build fails to link, not at run time.
   - Kept: the whole-program translation, the default of `compile`, for the seed, `bootstrap/ulang.c`, which stays one self-contained C file, and for `make selfcompile`, which compares such files.
   - Lost: `cc` no longer inlines functions of other packages, such as those of `option`, into their users; inlining at the level of ulang (Compiler 3) gets it back, since the front end sees the sources, and `-flto` meanwhile, at the cost of time.
   - Clash: a project with a directory `prelude/` at its root, which already clashes with the library in C, gets duplicate symbols when linking, which `CLAUDE.md` states.
   - Steps: the archive of `prelude`, linked by the binary of the tests; then any package, and the tests of `ulang/` against the archive of `ulang`; then `ulang.bin build` (item 1) building and caching the archives of the packages a program loads.

## Compiler

1. **Runtime errors have no positions.** Solution: positions in the messages of the runtime and of the interpreter, first for uncaught exceptions and failed `assert`s, from the positions that the checked program keeps (`At` of `ulang/syntax/syntax.u`).
2. **Programs need a C compiler**, and `cc -O2` takes most of the time of `make selfcompile`. Solution: a backend that writes assembly for x86-64, see `assembly.md`.
3. **No optimizations.** Solution: passes between checking and translating to C, e.g. inlining small functions, folding constants, the rewrites of Diagnostics 5, and loops for folds of comprehensions beyond `list.foldr` into lists, such as those of sets and maps and of several generators.

## Verification

1. **Contracts and proofs** are not implemented, only lemmas with the default proof, see `prove.md`, where functions have only `requires`, which states their domain, also that of the builtins, e.g. `requires d != 0` of `/`, so that the exceptions of builtins, which no `raises` counts, are ruled out. Solution: parse specifications and proofs, and prove them with the simplifier of `prove/`.
2. **How strongly an obligation is established is not recorded.** Ideas, which need a design of their own: a status per obligation, proven, tested (Testing 1), or open; trusted facts by `assume … why "…"`; a command `ulang.bin audit <file>` that lists the assumptions and the obligations that depend on them; and runtime checks of the obligations that are not proven.

## Later

1. **Procedures may do anything that `os` offers**, invisibly in their signatures. Solution: a clause `uses os` on exported procedures.
2. **Failures of programs that read files or arguments are hard to reproduce.** Solution: `run` records the results of the `os_*` procedures and replays them.
3. **No native code of users.** Solution: `builtin` sections outside the library, with the native definitions linked in by `ulang.bin build` (Build 1).

## Rejected and decided

- **A faster `ulang/run/run.u`** by numbering the names of declarations and variables when a program is loaded, so that the environments compare integers, and **integers tagged in the pointer** in the runtime, to save the boxes of most integers: both rejected.
- **Hash consing** of all constructors and tuples in the runtime, tried and removed (`be1808d` is the state without it): 70% of the constructions of the compiler and 85% of `run.u` equal a live value, and peak memory fell by 40–57%, but it was 2.2–2.5 times slower from cache misses, a bucket, its entry, and the candidate for every construction. **Maps and sets ordered by hash** were 18% slower for the compiler and 75% for `run.u`, since hashes outside -16..255 are boxed and `Name` keys differ early anyway. Consing particular structures, such as types or the terms of `prove/`, for memory or identity is still open.
- **A stack machine** for the interpreter, whose stack and code would be lists or maps, and **mutable arrays**, which values shared by two variables, atomic effects, and the restoring of variables by `try` exclude: rejected.
- **Partial field accesses** marked at the access, as `e!f`, or rejected statically: dropped, `MissingField` stays.
- **View patterns** `f -> p` beside the pattern aliases: rejected, since they call a function, which defeats the exhaustiveness check and need not terminate; pattern aliases are expanded instead. **Aliases of qualified names**, `Qualified(module, base)` for `Name(Some(module), base)`: not worth it.
- **Refutable patterns in generators**, such as `for Some(x) in xs`: rejected, both skipping the elements that do not match, as in Haskell, which hides a filter in the pattern and silently drops elements whose shape a mistake changed, and failing at run time, which makes a generator partial. Generators bind only irrefutable patterns (the forms), and a filter is a guard, `for o in xs if o != None`, or a `match` in the element.
- **A form `fold(let n := 0; for x in xs if p(x) yield n + 1)`** of a loop that accumulates: not unless code shows a need, since `foldl` and a `for` statement already write it, and agents do best with one way of each.
- **`call`, `assign`, and `skip`** stay, **`in`** stays at calls, **`test name()`** keeps its parentheses, and **`[…]`** stays for type arguments, while containers are written by the forms `List(…)`, `Set(…)`, `Map(…)`, and `Array(…)`; delimiters, `[…]` for lists, `{…}` for sets and maps, and `|…|` for arrays, were set aside, since the empty set and the empty map need two texts that `show` can print, `{}` and `{=>}`, and `|…|` does not nest, `||1|, |2||`; a `[…]` for lists alone stays possible on top of the forms.
- **Guards that bind**, such as `if let`, for code that tests `!= None` and then matches again: rejected; such code is one `match` over a function that classifies the case once, as `fusion_of` of `ulang/compile/compile.u` does for the calls that compile to loops.
- **User-defined notations** stay, although parsing depends on the imports.
- **`++` of arrays** is deferred, since arrays are built by forms.
- For the forms: no **`break`**, since a `for` runs to the end and an early exit goes through `while` or an exception; no **`Seq` type** or comprehensions without a form, since the form says what is built; no **choice of the result by the expected type**, the problem of Scala's `CanBuildFrom`, which violates locality; and no **`let` between generators** until code needs it.
- **Chains of conditions**, by `elif` or by a `when` with arms `if c => …`, tried and removed: `if` always nests, and an `if` after `else` is an `if` in its body, with its own `end`.
- **`Char`** stays a type of its own.
- **Functions may raise**, where `requires` states their domain (Verification 1).
- **Subpackages private to their parent, with re-exports** from the parent, as in Rust (`pub use`): rejected, since importing a subpackage from elsewhere is sometimes useful, and a re-export is a second way to reach the same declarations, the one transitive import, after which an import line no longer names the package that its names come from.
- **Imports relative to the importing file**, as in JavaScript, Zig, and the `#include "…"` of C: rejected for imports from the root, although they read each file in isolation and keep the imports of a subtree that moves, since a package then has a spelling per place, its importers are found only by a pattern, chains of `../` grow with nesting, and dependencies need a second form anyway, so that projects in JavaScript add path aliases and Python recommends absolute imports.
- **Overloading by type within a module**: tried and removed. Within a module, functions overload only by their number of arguments, and by type only across modules, which qualify their names, also across the files of a package. Telling apart the declarations of one name and arity in one module took an encoding of their types into their names, `f{(T) -> R}`, undone wherever names were compared, since a function is known by its module, name, and arity in `Sig`, `Defs`, and both backends; two hooks of one name, such as the shows of two datatypes, go into two modules.
- **A drastically faster interpreter**: rejected; it is about 300 times slower than compiled code, e.g. 11 seconds against 35 milliseconds for a case that loads the library, and minutes against 2 seconds for parsing the sources of the compiler, so such tests run only compiled, `ulang/test/errors/` by `project.u` and the checks of `checks/` by their `main`. The quick loop of an agent on large inputs is compiled tests, `test --compiled` of Build 1, not the interpreter.
- **The runner of the binary of the tests in ulang**, as a private procedure of `ulang/prelude/os.u` over procedure values of the tests, which `main` would build: rejected; it would still be a second copy of the selection of `ulang/ulang.u`, which the library cannot import, and couple `ulang/compile/compile.u` to a private name of the library, so the selection stays in C, `u_run_tests` of `ulang/runtime/ulang.c`.
