## Testing

1. **Properties are only tested on the examples written by hand**, and the formals of tests are reserved but rejected. Solution: tests with formals, `test append_size(xs: List[Int], ys: List[Int]) := assert …`, which the runner calls on generated values of the types of the formals, deterministically, and which report the values of a failure. They give the evidence "tested" of Verification 5.
2. **What a function does is seen only from its body or from tests elsewhere**: a signature gives the types, a doc gives prose that nothing checks and that goes stale, and the tests of a function sit apart from it, often in another file, private to their module, so neither a reader of the `export` section nor an importer, nor an agent that reads a signature or `ulang.bin sig` (Diagnostics 5), sees a concrete call with its result. Solution: examples as part of a signature, checked and run, documentation that cannot go stale:
   - **Syntax**: clauses `example` between the signature and `:=`, or after a signature without body in `export`, one per line, where `example` becomes a keyword:
     - of a function, an equation of a call and its result, `example gcd(12, 18) == 6`, or a call that raises, `example chr(-1) raises NoCharacter(-1)`;
     - of a procedure, a call whose arguments for the outs are the expected values, `example divmod(in 7, 2, out 3, 1)`, and a ref given as before and after, `example push(in 3, ref List(1) => List(3, 1))`, or `raises` as for functions.
   - **Where**: on the first occurrence of a signature, in `export` for the exported ones, which the definition in `implementation` does not repeat, as it repeats the signature, so an importer sees them; on the definition for private ones. An example of an export section names only what the export sees, the exports of the module and its imports, so it is a call that an importer could write; so an example of an abstract type builds its values by the exported functions, `example size(insert(1, empty())) == 1`.
   - **Checking**: an example is a closed expression of type `Bool`, without locals, whose call names the declaration it belongs to, resolved by the overloading of the module, so `example size(List(1)) == 1` of `set.size` is an error. It is checked with the module after its declarations, and respects the `requires` of the function (Verification 1), which an example outside its domain violates.
   - **Running**: `ulang.bin test` runs the examples of a file as tests of their own, named `name.example.N` with `N` from 1 in the order of the source, in both backends, also by `make testc`, and a failure shows both sides, `example 1 of gcd failed: gcd(12, 18) gave 3, expected 6`; examples of the library run with the tests of `prelude/`. `ulang.bin sig`, the hover of the VS Code extension, and the `▶ Run` links show them.
   - **Uses**: tests of one call each, such as `test paths()` of `prelude/os.u` for `os_dirname`, become examples of their functions; the examples are the first values that the generated tests of item 1 try; and examples are obligations that the prover checks against the contracts of Verification 1 by evaluation, a cheap check that a contract is not false.
   - **Not**: examples in docs, as Python's doctests and Rust's examples in `///` are, since docs are not checked and their text would need a parser of its own; and examples with free variables, which are properties, item 1.
   - Then a rule of style in `CLAUDE.md`, that an exported function whose name and types leave its meaning open has an example, e.g. of the order of its arguments, and `format` printing the clauses.

## Modules

1. **The layers of the compiler are a convention only**: `ulang/` is one package of all its files, so any file may use any other, and `prove/` cannot use the parser or the checker without seeing the whole compiler. Solution: after the moves of Code 4, `ulang/` split into subpackages, e.g. `ulang/syntax`, `ulang/check`, and `ulang/backend`, whose acyclic imports check the layers, and `prove` importing those it needs.
2. **`os` is a member of the library**, so every module sees the procedures of the system without importing them. Solution: `os` as a package of its own, imported by what uses it, after an experiment that shows which uses become ambiguous.
3. **Names cannot be qualified by their package**, so two imported packages that declare a type of the same name make every use of it `Ambiguous` (`normalize` of `ulang/check.u`), and a clash that overloading by type cannot decide has no way around it but renaming. For example, `prove/` cannot import `ulang` without renaming its `Expr`, `Type`, `Name`, `Var`, `Pat`, and `Branch`, and maybe its constructors `EApp`, `ELam`, `EIte`, `EMatch`, and `ERaise` (`prove.md`, the plan). The checker already resolves qualified uses: `visible_names` and `overloads` take `Name(Some(m), base)` as exactly the declaration of module `m`. What is missing is syntax, and a meaning of the qualifier as a package. Solution:
   - **Qualifiers**: the last name of the path of each imported package, `ulang` for `import "ulang"` and `nested` for `import "tests/modules/paths/nested"`, written `q.x`. Two imports with the same last name are a parse error until there is a need for `import "…" as q`. A package whose last name is a keyword cannot be qualified. Possibly also the own package and `prelude`.
   - **Where**: in types, `ulang.Expr`, and in patterns, `case ulang.EApp(f, args) =>`, where `.` does not occur now, so the parser builds the qualified name directly. In expressions, `ulang.size(xs)` parses as the field access `EField(EVar(ulang), size)`, which the checker reads as a qualified name when its base is a qualifier. That needs no state of imports in the parser, and is unambiguous since a formal, local, or pattern variable of the name of a qualifier is an error, as `HiddenLocal` is.
   - **Meaning**: a qualified use has as its candidates the exported declarations of the members of that package, among which overloading by type still decides. It never reaches private declarations, unlike the exact `Name(Some(m), …)` of checked code, which `overloads` takes without `is_visible`.
   - **Representation**: the parsed name needs a mark that it names a package, not a module. The ids can coincide: the program `tests/modules/paths.u` has the module id `tests/modules/paths` and imports the package `"tests/modules/paths"`. Options are a field of `Name`, or a constructor of uses that the checker replaces; not an encoding in the string (Code 2). `format` prints the qualifier as written.
   - **Nearness for types**, to decide with it: a type of the module hides those of other modules already, and the library's are hidden by any module's. If the members of the own package also hid the types of imported packages, `prove/simp.u` would keep writing `Expr` for its own, and only `prove/translate.u` would write `ulang.Expr`, instead of every file of `prove/` qualifying both.
   - Then `CLAUDE.md`, under Modules and Overloading, where "the parser builds no qualified names", and the highlighting of the VS Code extension; tests of qualified types, patterns, and calls, of a qualifier hidden by a local, of a clash of qualifiers, and of a qualified private name.

## Build

1. **Building and testing are spread over the Makefile, `testc.sh`, and the commands of `ulang.bin`**: compiled programs are linked by hand, with `-DULANG_LIB`, `-I ulang/runtime`, the runtime, `-lgmp`, and `-lgc`; `testc.sh` compiles, runs, and judges each file in shell, by `xargs -P`, and leaves the C of earlier runs in `out/testc/`; and `project.u` only marks the root, without the programs of a project or where outputs go. Solution: `ulang.bin` as the one tool, as `cargo` is for Rust, which calls the C compiler itself, and a Makefile that only builds the seed.
   - Processes: builtin procedures of `os` that start a process with arguments and wait for its status, also several at once for parallel jobs, e.g. `os_spawn` and `os_wait`, in both backends, where the interpreter uses those of the host.
   - `ulang.bin build <file> [<entry>]` checks, compiles to C, and links a binary, all in `out/` of the project: the runtime as an object compiled once and kept, the C compiler from `CC` or `cc`, the flags and libraries in one place of the tool, and the paths of the library and the runtime fixed when the tool is built, as `ULANG_LIB` is now. A build is redone when a hash of its inputs differs, the loaded modules, the runtime, the flags, and the tool, recorded next to its outputs, not by times.
   - `ulang.bin test --compiled <dir> …` judges each file as `test <dir>` does, built with the entry `test`, in parallel jobs, which replaces `testc.sh`.
   - Project: `project.u`, now a doc only, becomes a module that `ulang.bin` reads with the interpreter, as Zig reads `build.zig`, so that the metadata stays in ulang files, typed by the checker: the programs as values, e.g. `Program("ulang", "ulang/ulang.u", "main")`, and the directories of tests; `ulang.bin build` and `ulang.bin test` without paths take them from it. It is never a member of the package of its directory.
   - The Makefile keeps only the seed, `bootstrap/ulang.bin` from `bootstrap/ulang.c`, and targets that call `bootstrap/ulang.bin build` and the tool, while the check of the fixed point becomes `ulang.bin selfcompile`, which compiles the compiler twice and installs the seed as `make selfcompile` does now.
   - Later: dependencies of a project, by path and then by the URL and commit of a repository, declared in `project.u`, fetched into a cache outside the project, with a lock file of their hashes, and imported by paths whose first segment is the name that `project.u` gives them, as Go's module paths. Compiler 2 would remove the C compiler from all of this.
   - Steps: the procedures of processes; `build` of one file; `test --compiled`, after which `testc.sh` goes; the project file; the Makefile reduced to the seed; then dependencies.
2. **Every compiled program contains the C of all the packages it loads**, which `cc` parses again for each program: the library is about 106 KB of the 123 KB of `tests/strings.u`, about 70 ms of its 175 ms of `cc -O2`, and each test file of `ulang/` compiles the whole package of the compiler, so that `make testc` repeats the same C for every file. Solution: packages compiled separately, each once, into a static archive, which programs link, with the library as the package `prelude`, a case of the same mechanism, not a special one; no shared libraries, which would need position-independent code, rpaths, and versions of their own, for no gain in binaries that tests throw away. The plan in detail is `archives.md`.
   - What makes it possible: every value is a `u_value`, without specialization by type, so one compiled `list.foldr` serves all callers; checked programs carry only resolved names, `Name(Some(m), …)`, which `mangle` and `c_text` of `ulang/compile.u` make stable C names; and orders, equality, and show are reached through the descriptors `t_…` of the types, not called by the users of a type.
   - A package: `compile --package <dir> <out>` writes the C of its members, without their tests, with the exported declarations and the descriptors of exported types `extern`, the private declarations with hidden visibility, so that the tests of a member, which see its private declarations, can link them, and `static` only what nothing outside the C file reaches. With it go what each program now gets for every module it loads: the functions without parameters as globals computed at the first use, the accessors and updaters of fields, and the wrappers `wp_` of its procedures; the formats `u_text_*` go into the runtime or the archive of `prelude`. One C file and object per member; each unit declares what it references of other modules itself, from `Defs`, without generated headers. Each function in a section of its own, `-ffunction-sections`, so that the linker, by `--gc-sections`, keeps only what is reached, which replaces the pass of Compiler 3.
   - A program: `compile` emits only the modules of the program, or for the tests of a member that member, and links their archives, `out/lib/<package>.a`, with the runtime in the archive of `prelude`; the front end still parses and checks the packages it loads, which takes tens of milliseconds, and a cache of their `Sig` waits until that matters.
   - Staleness: each archive is rebuilt when a hash of its inputs differs, the sources of its members, the stamps of the packages it imports, the runtime, the flags, and the tool, as in Build 1, and the hash is a symbol of the archive, which each unit that uses the package references, so that a program linked with an archive of another build fails to link, not at run time.
   - Kept: the whole-program translation, the default of `compile`, for the seed, `bootstrap/ulang.c`, which stays one self-contained C file, and for `make selfcompile`, which compares such files.
   - Lost: `cc` no longer inlines functions of other packages, such as those of `option`, into their users; inlining at the level of ulang (Compiler 4) gets it back, since the front end sees the sources, and `-flto` meanwhile, at the cost of time.
   - Clash: a project with a directory `prelude/` at its root, which already clashes with the library in C, gets duplicate symbols when linking, which `CLAUDE.md` states.
   - Steps: measure `make testc` per file, to confirm that the files of `ulang/` take most of its time; the archive of `prelude`, linked by `testc.sh`; then any package, and the tests of `ulang/` against the archive of `ulang`; then `ulang.bin build` (item 1) building and caching the archives of the packages a program loads.

## Diagnostics and refactorings

1. **Positions are only those of commands**: `ulang/syntax.u` keeps a position in `Top` only, so type errors are reported at their declaration, not at the expression, and no use of a name can be found again, which queries and renaming need. Solution: positions on the uses of names in the parsed tree, variables, the names of calls, and constructors in patterns, and the checker records, for each, the qualified name it resolved to and its type; no spans, since refactorings print the tree again (item 5). Compiler 1 can carry them on.
2. **A run reports only the first error, as a line of text**, which tools and agents parse, and the VS Code extension by a regular expression. Solution: all errors in one run, where the checker continues after an error with the next command, taking the declared signature of the failed one, and the parser resumes at the next command, a keyword in column 1; and a datatype `Diagnostic` in `ulang/error.u` with a stable code, the constructor of the error, e.g. `CannotUnify`, the file and position, and fields such as the expected and found types, the candidates with their types, or the missing patterns. It is printed as text by default, the style of GCC that editors and agents read, with indented lines `key: value`, e.g. `tests/a.u:12.7: error[CannotUnify]: cannot unify Int and Str`, `  expected: Int`, and by `--format=jsonl` one object per line, for the extension. Success prints nothing or one line, and the exit status tells parse, type, test, and internal errors apart. Tests of errors state their code and position, `// error[CannotUnify] at 3.1`, independent of the wording of messages.
4. **Errors do not suggest their fix** where the checker knows it. Solution: suggested edits as refactorings (item 6), e.g. the missing cases of a match, or a qualified name for an ambiguous use, listed with the diagnostic and carried out by `--apply`.
5. **The resolution of names is invisible**, and finding the uses of a declaration needs reading, since `size` in a file that imports `set` and `map` may be any of three. Solution, on top of item 1: `ulang.bin resolve <file> <L.C>`, the qualified name, type, and declaration of the use there, also as hover in the VS Code extension; `ulang.bin refs` of a use or of `module.name/arity`, all its uses in the files that import it; `ulang.bin sig <module>`, the exported signatures without bodies; and `check` of several files or a directory in one process.
6. **No refactorings**, so renaming a declaration means finding its uses by hand. Solution: refactorings as changes of the parsed tree, printed by `format_program`, which keeps docs since they are syntax: refused unless the file is formatted, which `check` ensures; checked again after; and refused if any other use resolves differently from before, which makes them safe under overloading without reasoning about it. They print a diff, or write the files with `--apply`. In order: rename, filling in the missing cases of a match, adding a field to a constructor with its constructions and patterns, and changing a signature with its calls; not extracting or inlining, which edits of the text do well enough.
7. **Code that could be simpler is only found by reading it**, e.g. `List(for e in List(for x in m) …)` instead of `for k => v in m`, the same projection `List(for x in xs yield x.name)` repeated, a hand-written `match` on `get(…)` that is `value_or`, or a collecting loop `xs := xs ++ List(v)` instead of a `Buffer`. Solution: rewrites on the checked syntax tree, each from a pattern to a simpler term that keeps the meaning, which `ulang.bin check --lint` reports as warnings with the position and the replacement, opt-in, since warnings that a run always prints are noise that agents either chase or learn to ignore, which `--apply` carries out as a refactoring, and which the compiler may apply as the optimizations of Compiler 4; each rewrite has a test of the source that triggers it and of the result.

## Overloading

1. **Generic code over containers is impossible**, e.g. `function f[C](c: C) := size(c)`, nothing states what `size` must satisfy, and the hooks `compare`, `==`, and `show` are unchecked, with `Unordered` and `Incomparable` at run time. Deferred: named signatures, implemented by modules (`implements container with C[A] := Set[A]`), modules with parameters instantiated at the import (`import stats[set]`), one canonical implementation per type, and signatures `eq`, `ord`, and `show` that replace the hooks, where a missing implementation is a type error. Also open: laws as items of signatures, discharged once per implementing module. Until then, the hooks stay; and not before `resolve` and `refs` (Diagnostics 5), since modules with parameters resolve names by what no use shows.

## Checker

1. **Failure is not in the types**: a procedure can raise any value without saying so, so a caller cannot see what may fail, and the checker cannot tell whether the handlers of a `try` are exhaustive. Solution: `raises E, …` on procedures, required in `export` and inferred inside a module, of declared datatypes only, by convention one error datatype per module. Every `raise`, and every call that can raise, is covered by a `try` or by the `raises` of the caller, the handlers are checked for exhaustiveness over the declared types, and procedure types carry their `raises` as written, without polymorphism over sets of exceptions. Open: how exceptions of functions outside their `requires` (Verification 1) count for the `raises` of a procedure, and a way to turn a raise into a value, instead of the pattern `failed: Option[TypeError]`, e.g. a `try` expression.
2. **Termination is a style rule only**, so the split between functions and procedures guarantees nothing, and unfolding a function that does not terminate can prove false. Solution: the checker accepts recursion in functions only if it is structural on a parameter of a datatype, or decreases a measure declared by `decreases` after `:=`, whose decrease is an obligation of the prover, and otherwise reports an error that advises a procedure.
3. **Local `let`s are generalized**, which is rarely used and complicates inference once types carry more, such as `raises`. Solution: generalize only top-level declarations, which carry their types anyway.

## Syntax

1. **Folds cannot stop early, and the bounded quantifiers are missing**: `and` and `or` short-circuit in both backends, which stays, but a fold always walks its whole container, so `exists` and `forall` of the containers skip `p` once decided but still visit every element, and a search cannot end at its first hit; and `exists` and `forall` clash with the quantifiers of specifications (`prove.md`, open point 15). Solution: folds that take a test of the accumulator, after which they stop, `foldl(c, acc, stop, f)`, by which `exists` and `forall` stop at the first decision. Deferred, not convinced yet, since each is one more way to write a loop: bounded quantifiers `forall x in c => e` and `exists x in c if q => e` with the generators of the forms, where the unbounded `forall x: T => e` occurs only in specifications, which read the bounded ones as `forall x => contains(x, c) ==> e`, which translate to the stopping folds. The functions `exists` and `forall` of the containers stay until then.
2. **Errors show pattern aliases expanded**: `NotExhaustive` and `Unreachable` print the constructors that an alias stands for, e.g. `missing Some(false)` or `unreachable case Some(true)` where the case is written `Yes()`. Solution: fold a witness or a case back into the aliases whose stored patterns match it (`PatAlias` of `ulang/sig.u`) before printing, preferring the alias that covers most.

## Library

1. **No binary data**: strings are code points, and the procedures of `os` read and write UTF-8 only, so a file that is not UTF-8 cannot be read. Solution: a type `Byte` with `Array[Byte]`, and procedures of `os` that read and write bytes, with explicit encodings between them and strings.

## Compiler

1. **Runtime errors have no positions.** Solution: positions in the messages of the runtime and of the interpreter, first for uncaught exceptions and failed `assert`s, from the positions of Diagnostics 1.
2. **Programs need a C compiler**, and `cc -O2` takes most of the time of `make selfcompile`. Solution: a backend that writes assembly for x86-64, see `assembly.md`.
3. **Compiled programs contain the C of the whole library**, since every module sees it, which the C compiler parses although it drops what nothing reaches: the generated C is `static` except what `ulang/runtime/ulang.h` declares extern (`runtime_referenced` of `ulang/compile.u`, `Linkage` of `ulang/c.u`), which took `cc -O2` of `tests/strings.u` from 1.4 s to 0.2 s, its code from 97 KB to 44 KB, and `make testc` from 99 s to 20 s, but the C of a small test is still about 120 KB, and the compiler's `cc -O2` takes 10 s. Solution: packages compiled separately into static archives (Build 2), whose linker keeps only what is reached.
4. **No optimizations.** Solution: passes between checking and translating to C, e.g. inlining small functions, folding constants, the rewrites of Diagnostics 7, and loops for folds of comprehensions beyond `list.foldr` into lists, such as those of sets and maps and of several generators.

## Verification

1. **Contracts and proofs** are not implemented, only lemmas with the default proof, see `prove.md`, where functions have only `requires`, which states their domain, also that of the builtins, e.g. `requires d != 0` of `/`. Solution: parse specifications and proofs, and prove them with the simplifier of `prove/`.
2. **Defects of the prover**: `merge` gets fresh fuel inside a cycle, from `add_ineq` with 10 through `add_pair` and `readd_ineqs`, so it is not bounded. Solution: one fuel for the cycle.
3. **Fuel and limits of the prover are numbers spread over the code**, 3, 5, 10, 20, 60, and 64, and the context is built positionally, as `Ctx(…, false, 3, 0, 2)`. Solution: a record of named limits in one place.
4. **How strongly an obligation is established is not recorded.** Ideas, which need a design of their own: a status per obligation, proven, tested (Testing 1), or open; trusted facts by `assume … why "…"`; a command `ulang.bin audit <file>` that lists the assumptions and the obligations that depend on them; and runtime checks of the obligations that are not proven.

## Later

1. **Procedures may do anything that `os` offers**, invisibly in their signatures. Solution: a clause `uses os` on exported procedures.
2. **Failures of programs that read files or arguments are hard to reproduce.** Solution: `run` records the results of the `os_*` procedures and replays them.
3. **No native code of users.** Solution: `builtin` sections outside the library, with the native definitions linked in by `ulang.bin build` (Build 1).

## Rejected and decided

- **A faster `ulang/run.u`** by numbering the names of declarations and variables when a program is loaded, so that the environments compare integers, and **integers tagged in the pointer** in the runtime, to save the boxes of most integers: both rejected.
- **Hash consing** of all constructors and tuples in the runtime, tried and removed (`be1808d` is the state without it): 70% of the constructions of the compiler and 85% of `run.u` equal a live value, and peak memory fell by 40–57%, but it was 2.2–2.5 times slower from cache misses, a bucket, its entry, and the candidate for every construction. **Maps and sets ordered by hash** were 18% slower for the compiler and 75% for `run.u`, since hashes outside -16..255 are boxed and `Name` keys differ early anyway. Consing particular structures, such as types or the terms of `prove/`, for memory or identity is still open.
- **A stack machine** for the interpreter, whose stack and code would be lists or maps, and **mutable arrays**, which values shared by two variables, atomic effects, and the restoring of variables by `try` exclude: rejected.
- **Partial field accesses** marked at the access, as `e!f`, or rejected statically: dropped, `MissingField` stays.
- **View patterns** `f -> p` beside the pattern aliases: rejected, since they call a function, which defeats the exhaustiveness check and need not terminate; pattern aliases are expanded instead. **Aliases of qualified names**, `Qualified(module, base)` for `Name(Some(module), base)`: not worth it.
- **Refutable patterns in generators**, such as `for Some(x) in xs`: rejected, both skipping the elements that do not match, as in Haskell, which hides a filter in the pattern and silently drops elements whose shape a mistake changed, and failing at run time, which makes a generator partial. Generators bind only irrefutable patterns (the forms), and a filter is a guard, `for o in xs if o != None`, or a `match` in the element.
- **A form `fold(let n := 0; for x in xs if p(x) yield n + 1)`** of a loop that accumulates: not unless code shows a need, since `foldl` and a `for` statement already write it, and agents do best with one way of each.
- **`Option` as a container** of at most one element, as in Scala and Rust: not needed for Checker 4, a separate question.
- **`call`, `assign`, and `skip`** stay, **`in`** stays at calls, **`test name()`** keeps its parentheses, and **`[…]`** stays for type arguments, while containers are written by the forms `List(…)`, `Set(…)`, `Map(…)`, and `Array(…)`; delimiters, `[…]` for lists, `{…}` for sets and maps, and `|…|` for arrays, were set aside, since the empty set and the empty map need two texts that `show` can print, `{}` and `{=>}`, and `|…|` does not nest, `||1|, |2||`; a `[…]` for lists alone stays possible on top of the forms.
- **Guards that bind**, such as `if let`, for code that tests `!= None` and then matches again: rejected; such code is one `match` over a function that classifies the case once, as `fusion_of` of `ulang/compile.u` does for the calls that compile to loops.
- **User-defined notations** stay, although parsing depends on the imports.
- **`++` of arrays** is deferred, since arrays are built by forms.
- For the forms: no **`break`**, since a `for` runs to the end and an early exit goes through `while` or an exception; no **`Seq` type** or comprehensions without a form, since the form says what is built; no **choice of the result by the expected type**, the problem of Scala's `CanBuildFrom`, which violates locality; and no **`let` between generators** until code needs it.
- **Chains of conditions**, by `elif` or by a `when` with arms `if c => …`, tried and removed: `if` always nests, and an `if` after `else` is an `if` in its body, with its own `end`.
- **`Char`** stays a type of its own.
- **Functions may raise**, where `requires` states their domain (Verification 1).
- **Subpackages private to their parent, with re-exports** from the parent, as in Rust (`pub use`): rejected, since importing a subpackage from elsewhere is sometimes useful, and a re-export is a second way to reach the same declarations, the one transitive import, after which an import line no longer names the package that its names come from.
- **Imports relative to the importing file**, as in JavaScript, Zig, and the `#include "…"` of C: rejected for imports from the root, although they read each file in isolation and keep the imports of a subtree that moves, since a package then has a spelling per place, its importers are found only by a pattern, chains of `../` grow with nesting, and dependencies need a second form anyway, so that projects in JavaScript add path aliases and Python recommends absolute imports.
- **Overloading by type within a module**: tried and removed. Within a module, functions overload only by their number of arguments, and by type only across modules, which qualify their names, also across the files of a package. Telling apart the declarations of one name and arity in one module took an encoding of their types into their names, `f{(T) -> R}`, undone wherever names were compared, since a function is known by its module, name, and arity in `Sig`, `Defs`, and both backends; two hooks of one name, such as the shows of two datatypes, go into two modules.
