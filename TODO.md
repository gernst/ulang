## Modules

1. **Modules are known by name and resolved against the directory of the main file**, so nothing imports across directories, `self/syntax.u` and `prove/syntax.u` cannot both be loaded (Verification 2), siblings repeat their imports of each other, and they cannot depend on each other cyclically. Solution: each directory is a package, the files of which read each other's exports.
   - Identity: a module is its path from the root without `.u`, e.g. `self/check`, in `Name.module`, in the ` in m` of errors, and in mangled names, while library modules keep their bare ids (`map`, `str`), so the backends and `ulang.h` keep theirs. The root is the nearest directory above with a marker file, e.g. `ulang.project`, else the directory of the main file, never the working directory.
   - Within a package: every file sees the exports of all its sibling files, with their notations, without imports; the implementation sections and the constructors of abstract types stay private to their file. The checker takes a package in three phases over all its files, the datatypes and abstract types, then the signatures, then the bodies, which the complete signatures of the export sections allow, so siblings may depend on each other cyclically. The parser first reads the notations of all export sections and parses every file with their union. Two exports of one name and arity in one package are an error, so that adding a file makes no use in another ambiguous, and with Overloading 1 two whose types unify.
   - Programs: files without sections are not members of the package, but see its exports, e.g. the programs of `tests/` and `self/ulang.u`; the error tests of non-transitive imports and private names (`wrapper.u`, `inner.u`, `hiding.u`, …) move into subdirectories of their own.
   - Between packages: imports per file, by path from the root and not transitive, preferably of a whole package, `import "prove"`, rather than of a file; packages are acyclic and checked after the packages they import. Modules below `p/internal/` are importable only from `p/` and its subdirectories. A subdirectory is a package of its own, without access to its parent or children other than by imports.
   - Library: flat, imported by name, `import "map.u"`; a package with a file named like a library module is an error.
   - Steps: identities and paths in the loader, then a bootstrap; the rule of names and arities; then packages loaded and checked as a whole, a bootstrap, and the migration of the sources; error tests of a missing package, an import of `internal/` from outside, a duplicate export within a package, and of `self/syntax.u` next to `prove/syntax.u`; then `CLAUDE.md` (Modules).
   - Open: whether imports name packages or files, and `internal/` versus a marker in the module.

## Overloading

1. **Within a module, overloading only distinguishes arities**, hence names like `zonk_type` and `zonk_expr`, or `UnknownProc` next to `UnknownProcedure`. Solution: overloading by type within a module as well, under the unique resolution, where two declarations of a name whose types unify are an error, with the declarations told apart by their types in `self/defs.u`, `self/run.u`, and `self/compile.u`, e.g. by mangled names.
2. **Generic code over containers is impossible**, e.g. `function f[C](c: C) := size(c)`, nothing states what `size` must satisfy, and the hooks `compare`, `==`, and `show` are unchecked, with `Unordered` and `Incomparable` at run time. Deferred: named signatures, implemented by modules (`implements container with C[A] := Set[A]`), modules with parameters instantiated at the import (`import stats[set]`), one canonical implementation per type, and signatures `eq`, `ord`, and `show` that replace the hooks, where a missing implementation is a type error. Also open: laws as items of signatures, discharged once per implementing module. Until then, the hooks stay.

## Checker

1. **Failure is not in the types**: a procedure can raise any value without saying so, so a caller cannot see what may fail, and the checker cannot tell whether the handlers of a `try` are exhaustive. Solution: `raises E, …` on procedures, required in `export` and inferred inside a module, of declared datatypes only, by convention one error datatype per module. Every `raise`, and every call that can raise, is covered by a `try` or by the `raises` of the caller, the handlers are checked for exhaustiveness over the declared types, and procedure types carry their `raises` as written, without polymorphism over sets of exceptions. Open: how exceptions of functions outside their `requires` (Verification 1) count for the `raises` of a procedure, and a way to turn a raise into a value, instead of the pattern `failed: Option[TypeError]` written three times in `self/`, e.g. a `try` expression.
2. **Termination is a style rule only**, so the split between functions and procedures guarantees nothing, and unfolding a function that does not terminate can prove false. Solution: the checker accepts recursion in functions only if it is structural on a parameter of a datatype, or decreases a measure declared by `decreases` after `:=`, whose decrease is an obligation of the prover, and otherwise reports an error that advises a procedure.
3. **Local `let`s are generalized**, which is rarely used and complicates inference once types carry more, such as `raises`. Solution: generalize only top-level declarations, which carry their types anyway.
4. **Locals may hide locals**, e.g. a pattern variable of a nested `match` or a formal of a lambda that hides a variable around it, a mistake that is not seen. Solution: an error when a formal, local, pattern variable, or formal of a lambda hides another of the same declaration, while locals may still hide declarations, since those depend on the imports. First: find the code in `self/`, `prove/`, `prelude/`, and `tests/` that hides locals on purpose, and what the error would break.

## Syntax

1. **Guards do not bind**, so code tests `!= None` and then matches again, with a case that cannot happen. Solution: conditions and guards that match a pattern and bind its variables in the branch they guard, e.g. `if let`.
2. **`fold` and the bounded quantifiers are missing**: a loop that accumulates is written as `foldl(c, acc, lambda …)`, and `exists` and `forall` of the containers are functions that clash with the quantifiers of specifications (`prove.md`, open point 15), which stop early (Self-hosted toolchain 8). Deferred, not convinced yet: `fold(let n := 0; for x in xs if p(x) yield n + 1)`, where `let` marks the binding of the accumulator, every `yield` and the initial value have the same type, the result is the final value, and the form runs to the end, with `foldl` and `foldr` of the modules as its translation; to consider: `fold` without parentheses, as the quantifiers are written, or the quantifiers with parentheses, as the forms are. Likewise bounded quantifiers `forall x in c => e` and `exists x in c if q => e` with the generators of the forms, where the unbounded `forall x: T => e` occurs only in specifications, which read the bounded ones as `forall x => contains(x, c) ==> e`; the functions `exists` and `forall` of the containers stay until then.

## Library

1. **No binary data**: strings are code points, and the procedures of `os` read and write UTF-8 only, so a file that is not UTF-8 cannot be read. Solution: a type `Byte` with `Array[Byte]`, and procedures of `os` that read and write bytes, with explicit encodings between them and strings.

## Compiler

1. **Runtime errors have no positions.** Solution: positions in the messages of the runtime and of the interpreter, first for uncaught exceptions and failed `assert`s.
2. **Deep recursion**: functions like `concat` over long lists recurse deeply, so compiled programs need `ulimit -s unlimited` for big inputs. Solution: a large stack for the main thread of compiled programs, as the interpreter has.
3. **Programs need a C compiler**, and `cc -O2` takes most of the time of `make selfcompile`. Solution: a backend that writes assembly for x86-64, see `assembly.md`.

## Diagnostics

1. **Errors are lines of text**, which tools and agents parse. Solution: `--json` for `check`, `test`, and `run`, with a stable code per error, the file, line, and column, the expected and found types, and the qualified names involved.
2. **Errors do not suggest their fix** where the checker knows it. Solution: suggested edits, e.g. the missing cases of a match, or a qualified name for an ambiguous use.
3. **The resolution of names is invisible**. Solution: `ulang.bin check --resolved <file>`, and hover in the VS Code extension, showing the qualified name that each use resolved to.
4. **Code that could be simpler is only found by reading it**, e.g. `list(for e in list(for x in m) …)` instead of `for k => v in m`, the same projection `list(for x in xs yield x.name)` repeated, a hand-written `match` on `get(…)` that is `value_or`, or a collecting loop `xs := xs ++ list(v)` instead of a `Buffer`. Solution: program transformations on the checked syntax tree, each a rewrite from a pattern to a simpler term that keeps the meaning, which `ulang.bin check` reports as warnings with the position and the suggested replacement whenever the source would be transformed, `ulang.bin format --apply` carries out, and which the compiler may also apply as the optimizations of Self-hosted toolchain 1; each rewrite has a test of the source that triggers it and of the result.

## Verification

1. **Contracts, lemmas, and proofs** are not implemented, see `prove.md`, where functions have only `requires`, which states their domain, also that of their `raise`s and of the builtins, e.g. `requires d != 0` of `/`. Solution: parse specifications, lemmas, and proofs, and prove them with the simplifier of `prove/`.
2. **The simplifier of `prove/` reads its own syntax**, by `prove/read.u`, and does not see checked programs. Solution: a translation `self/prove.u` from the programs checked by `self/check.u`, with goals as `Bool` functions whose formals are the fixed variables, a default proof by simplification and induction on each formal of a datatype, where goals proven earlier are rules for later ones, and a command `ulang.bin prove <file>`, which needs the prover in `self/` or imports across directories, undecided.
3. **Defects of the prover**: `prove/read.u` parses the result type of a function and drops it; `merge` gets fresh fuel inside a cycle, from `add_ineq` with 10 through `add_pair` and `readd_ineqs`, so it is not bounded; and recursion is detected only for direct calls of a function to itself, so mutually recursive functions are unfolded as if they were not recursive, up to depth 64. Solution: keep the result type, one fuel for the cycle, and recursion by the strongly connected components of the calls.
4. **Fuel and limits of the prover are numbers spread over the code**, 3, 5, 10, 20, 60, and 64, and the context is built positionally, as `Ctx(…, false, 3, 0, 2)`. Solution: a record of named limits in one place.
5. **How strongly an obligation is established is not recorded.** Ideas, which need a design of their own: a status per obligation, proven, tested (Testing 1), or open; trusted facts by `assume … why "…"`; a command `ulang.bin audit <file>` that lists the assumptions and the obligations that depend on them; and runtime checks of the obligations that are not proven.

## Rejected and decided

- **A faster `self/run.u`** by numbering the names of declarations and variables when a program is loaded, so that the environments compare integers, and **integers tagged in the pointer** in the runtime, to save the boxes of most integers: both rejected.
- **Hash consing** of all constructors and tuples in the runtime, tried and removed (`be1808d` is the state without it): 70% of the constructions of the compiler and 85% of `run.u` equal a live value, and peak memory fell by 40–57%, but it was 2.2–2.5 times slower from cache misses, a bucket, its entry, and the candidate for every construction. **Maps and sets ordered by hash** were 18% slower for the compiler and 75% for `run.u`, since hashes outside -16..255 are boxed and `Name` keys differ early anyway. Consing particular structures, such as types or the terms of `prove/`, for memory or identity is still open.
- **A stack machine** for the interpreter, whose stack and code would be lists or maps, and **mutable arrays**, which values shared by two variables, atomic effects, and the restoring of variables by `try` exclude: rejected.
- **Partial field accesses** marked at the access, as `e!f`, or rejected statically: dropped, `MissingField` stays.
- **Refutable patterns in generators**, such as `for Some(x) in xs`: rejected, both skipping the elements that do not match, as in Haskell, which hides a filter in the pattern and silently drops elements whose shape a mistake changed, and failing at run time, which makes a generator partial. Generators bind only irrefutable patterns (the forms), and a filter is a guard, `for o in xs if o != None`, a guard that binds (Syntax 1), or a `match` in the element.
- **`call`, `assign`, and `skip`** stay, **`in`** stays at calls, **`test name()`** keeps its parentheses, and **`[…]`** stays for type arguments, but not for lists (the forms).
- **User-defined notations** stay, although parsing depends on the imports.
- **`++` of arrays** is deferred, since arrays are built by forms.
- For the forms: no **`break`**, since a `for` runs to the end and an early exit goes through `while` or an exception; no **`Seq` type** or comprehensions without a form, since the form says what is built; no **choice of the result by the expected type**, the problem of Scala's `CanBuildFrom`, which violates locality; and no **`let` between generators** until code needs it.
- **Chains of conditions**, by `elif` or by a `when` with arms `if c => …`, tried and removed: `if` always nests, and an `if` after `else` is an `if` in its body, with its own `end`.
- **`Char`** stays a type of its own.
- **Functions may raise**, where `requires` states their domain (Verification 1).
