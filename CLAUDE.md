# ulang

A minimal language with pure functional expressions, imperative statements, datatypes, and Hindley-Milner inference, implemented in itself in `ulang/`: parser, checker, interpreter, prover, and compilers to C and to x86-64, with a runtime in C (`ulang/runtime/`) and the library in `ulang/prelude/`. Each phase is a package of its own, which imports those before it, so the imports check the layers: `ulang/syntax`, `ulang/format`, `ulang/parse`, `ulang/expand`, `ulang/check`, `ulang/run`, `ulang/compile`, `ulang/prove`, `ulang/lint`, `ulang/refactor`, and `ulang/test`, with the driver `ulang/ulang.u` (Phases and packages of `doc/implementation.md`). The Scala 3 implementation it started from is on the branch `scala-baseline`.

This file has three parts: Workflow, the rules of working in this repository, the commands, and the tests; Language, the habits of other languages that fail and where to read what ulang means and how its implementation decides it; and Style, the conventions of the sources. The documentation of the rest is in `doc/`: `doc/language.md` the language and its principles, `doc/tool.md` the commands, `doc/implementation.md` the overview of the implementation, and `doc/implementation-notes.md` the detail of each phase. A new fact goes into the section of its topic, of this file or of `doc/`.

# Workflow

## Working rules

- A question asks for an answer, not an action: answer it, propose what suggests itself, and act only on an explicit go-ahead. Read-only lookups are fine.
- Checks:
  - After a refactor that keeps behaviour, `out/ulang.sh check ulang/ulang.u` and `check --test` of the changed files are enough: `check ulang/ulang.u` runs no tests of the packages it imports, which imports drop, so it misses the tests that build the changed datatypes.
  - After each edit, `ulang.sh format` the edited files and `ulang.sh check --test --prove` them, which takes seconds; `make` only when the built tool is needed, such as for `format` of a changed printer.
  - Run `make test` after changes of behaviour, in the worktree of the work, or when asked, and say that it ran; it runs the tests interpreted only, and the handover to `main` then runs only the tests that the work touches. Work split among sub-agents in worktrees runs it once, on the merge, by the session that merges their branches, while each agent runs only the checks of the point above. A small item, a few lines in one place, is done inline rather than by an agent, which must first read this file and the code around it.
  - Compiled tests and checks, `make testc`, `make testelf`, and `make testdocs`, only after asking, also the run that a new case of `ulang/test/errors/` takes its expected exception from. The machine is shared by several sessions, so run nothing only to measure, and run checks under `nice -n 19`.
  - Run tests and checks in a worktree of your own, never against the `out/ulang.bin` of the main tree, which other sessions rebuild while it runs, so that a test fails with internal errors such as `++ is not initialized`.
  - `make testc` only with a strong reason, e.g. changes to `ulang/compile/compile.u`, the runtime, or what the generated C depends on, and only after asking; a change of `ulang/compile/compile.u`, `ulang/compile/x86.u`, `ulang/compile/lower.u`, or the runtime runs `make testelf` next to it, so that both backends keep the same outcome.
  - `make testc`, after asking, on a change of what the cut load of imports keeps or computes, by which importers must see the same signatures, diagnostics, and hints as of the whole load: the declaration half of `check_package`, `signed_decls`, or `declared_cmd` of `ulang/check/check.u`, `Sig` or `exported` of `ulang/check/sig.u`, `declared_tokens` of `ulang/parse/parse.u`, or `hints` of `ulang/check/hints.u`; its tests of `ulang/test/declared/` cover each kind of declaration, and a difference that they miss gets a case there.
  - Time every phase of a run of checks and keep the output, so that questions about durations are answered from it; never rerun only to measure.
  - Redirect the output of `make` to a file, never pipe it into a command that may exit first, such as `tail -0` or `head`: `make` then dies of the broken pipe before linking, and a stale `out/ulang.bin` runs the next checks.
- Edit `.u` files through `ulang.sh refactor`, by its scripts of actions, not by text edits, `sed`, or rewriting the file, and brief sub-agents to do the same: its uses are how the tool improves, so each friction with it, an unclear refusal, a missing action, a slow or misleading reply, or a workaround, goes into `ideas/refactor.md` as an item, with the script and the reply.
- Edits by script: a replacement scripted against the text before `format` misses where `format` changed the layout, so a script asserts that each replacement matches exactly once and writes nothing otherwise; and `git add` with one path that does not exist stages nothing, so check what a commit holds.
- When `check` passes plainly wrong code, compare the errors that `check_all` of `ulang/check/check.u` returns with `diagnostics` of the checked program, which shows an error that the tree lost.
- Samples with lemmas over functions that may not terminate run under `ulimit -v` and `timeout`, since their tests grow memory without bound under `ulimit -s unlimited` (Testing 6 of `ideas/testing.md`).
- Commits: no `Co-Authored-By` for Claude; end the message with `Agentic Coding (<model>)`, e.g. `Agentic Coding (Claude Opus 5.5)`. Run `make` after every commit, so that `out/ulang.bin` is current.
- Other sessions may edit the same files, also those of `ideas/` and `CLAUDE.md`, at the same time: commit only the hunks of your own work, applied to the committed version, and leave theirs in the working tree.
- `ideas/` holds the open items, one file per area, listed in `ideas/index.md`, each item as the problem and the desired solution, named by its area and number, Testing 1 for item 1 of `ideas/testing.md`; delete an item when it is done. Explanations go into this file or the files of `doc/`.
- Plans and guides of work in progress, such as `ideas/gui.md`, are files of `ideas/`, versioned as all files are, and listed in `ideas/index.md`; delete each when its work is done, and what stays true afterwards goes into this file, the files of `doc/`, or the items of `ideas/`.
- Before making a word a keyword, search the sources for it as a name and rename those uses: the seed still takes it as a name, so `make` builds, and only the new lexer of `make test` rejects it.
- When working on ulang code, record in `unclear.md` each trip-up and unclear point: a wrong guess, a search that led nowhere, a doc that was stale or misleading, each as what was wrong and what is so, so that the documentation can be fixed from it.
- To compare a compiler before and after a change, e.g. the C that both compile from the same files, build the one before from the committed sources in a worktree of its own, never take the `out/ulang.bin` of the main tree, which other sessions rebuild from their uncommitted edits; the binary finds the library by the path that `-DULANG_LIB` compiled in, no variable of the environment, so its worktree stays until the comparison is done, and the outputs of two compilers also differ by their libraries if the change touches `ulang/prelude/`.
- No auto-memory: rules for later sessions go into this file, and only if it does not already say them.
- Finished work goes onto `main`, never left on a branch, in a worktree, or as a patch; a reverted experiment is no work, so say where its patch is. Work of several steps runs in a worktree below `.claude/worktrees/` on a branch of its own, each step committed there; to hand it over, merge `main` into the branch, run `make` and only the tests that the work touches, the files and cases it changed or affects, never all of `make test` again, then `git merge --ff-only` the branch in the main tree and `make`, and remove the worktree and the branch when the work is done.
- A new lint rule is run over the project before it is committed, each warning classified as a mistake or intended, and proposed with its count and samples of its sites, since false positives sink a rule; warnings that have an edit are fixed by `ulang.sh refactor @fix`, not by hand.
- Never add `volatile` to the generated C or to the runtime, not even as an experiment, and never propose it as a fix: it is not the solution to the miscompilations of `setjmp` by clang -O2, which are known, see `BUGS.md`. If a problem appears to have a real reason for `volatile`, stop and ask the user before writing it anywhere.
- Profile compiled programs with gprof, not perf, which cannot record call graphs here: build with `-pg`, run with `GLIBC_TUNABLES=glibc.gmon.maxarcs=50000000:glibc.gmon.minarcs=1000000`, and sum several runs by `gprof -s` if one has too few samples; gprof does not see time in shared libraries such as libgc.

## Commands

The commands, their options, and their replies are `doc/tool.md`; the facts that the rules above need:

- `make` builds `out/ulang.bin` and `out/ulang.sh` from the sources by the seed `bootstrap/ulang.bin`, about 15 seconds from nothing, 7 after an edit, and copies both to the root. Run every command by `out/ulang.sh`, which sets a large stack, never `out/ulang.bin` directly. Exit statuses: 0 success, 1 errors of the sources, 2 usage, 3 a failed run, test, or lemma, 4 an internal error.
- Every command runs the built `out/ulang.bin`, but the tests that `check --test` runs are interpreted, with the current sources of what they load, also of the compiler: after an edit of `ulang/`, its tests see the edit at once, while `run`, `format`, `hints`, and the checking by `check` itself see it only after `make`.
- `ulang.sh check [--lint] [--test [--timeout <seconds>]] [--prove] [<path>[:<name>] …]` checks files, directories, or by default the project; without `--test` and `--prove` it loads the imports only as far as the unit sees them, so it reports no errors in their definitions. `ulang.sh run <file>[:<procedure>]`, `ulang.sh hints <file>`, `ulang.sh compile <file> -o <target>` (`.c`, `.s`, or `.o`), and `ulang.sh compile --tests -o <target.c>` are the others.
- `ulang.sh format` rewrites files in the only layout that `check` accepts: run it on each `.u` file after editing it, and `make reformat` after a change of the printer.
- `ulang.sh refactor` edits sources by declaration and node, from scripts of actions, `@show`, `@put`, `@patch`, `@drop`, `@rename`, `@fix`, `@check test`, and the queries `@outline`, `@refs`, `@sig`, and `@resolve` (Refactoring of `doc/tool.md`); a script is one transaction and replies with the state, the new and gone diagnostics with the handles of their nodes, and its tests.
- `make test` is `check --test --prove` of the whole project, interpreted, about 35 seconds at a load of 3; `make testc` runs the tests compiled, about 7 seconds once built, `make testelf` compiled to objects, and `make testdocs` the checks of `checks/docs.u`, about 4 seconds.
- `make selfcompile` (about 15 seconds) and `make bootstrap` (about 4 minutes, a last resort) replace the seed only if the new compiler compiles itself to the same C. A new syntax reaches the sources one step after the commit that teaches it: that commit, then `make selfcompile`, and only then the sources that use it; branches that teach the seed merge one at a time, each followed by `make selfcompile`. A new builtin goes in with the runtime and `ulang/compile/lower.u` first, then `make selfcompile`, then its uses. A module moved out of the library keeps its file until `make selfcompile`.

## Tests

- Tests are named, `test name() := …` of `assert` statements, in the `implementation` sections of the members, where they reach private declarations, and in files without sections in the subfolder `test/` of the package they test: `ulang/test/` of the language, which the whole of `ulang/` implements, `ulang/prove/test/` of the prover, and `ulang/prelude/test/` of the library. Every file passes: the errors that a phase must raise are cases of `ulang/test/errors/`, see below. Names are distinct within a file, while members of a package may share them, since tests are private to their file, which selects and labels them. A test with formals, `test append_size(xs: List[Int], ys: List[Int]) := assert …`, is a property: the checker checks its body with the formals of their types, and the tester runs it on their enumerated values, as the test of a lemma, where each `assert` outside the body of a `try` or an `assert raises`, whose handlers could catch it, raises `Falsified` with the values of the formals and, of an equation, both sides, and a formal of a type that is not enumerable fails it with `Unenumerable` (`property_stmt` and `with_counterexamples` of `ulang/test/generate.u`); the runners and the backends skip the test with formals, which runs as the test of its name that the tester generates. Runs are entered by procedures without parameters, e.g. `procedure main() := …`. The examples of functions and procedures and the lemmas run as tests too, `f.example.N` and `l.lemma`, in the files that declare them, also of the library (under Specifications of `doc/implementation-notes.md`); a test of one call of a function is an example of it, `ulang/test/examples/` has those of the language.
- No test sits at the top of a `test/` but the lemmas of `ulang/prove/test/`: the programs that succeed are grouped by feature, one file per feature where their declarations do not clash, `ulang/test/expressions/`, `ulang/test/statements/` (also `for` and exceptions), `ulang/test/datatypes/` (also pattern aliases and orders, with their helper packages), `ulang/prelude/test/containers/`, `ulang/test/modules/`, `ulang/test/examples/`, a package whose examples run as its tests, `ulang/test/properties/`, of tests with formals, `ulang/prelude/test/os/`, whose `files.u` writes its files below `out/test/os/` of the root, since no directory of the sources but the root has an `out/`, and `ulang/prove/test/`, of lemmas; a new test joins the file of its feature, under a name that tells it apart there. No test runs longer than 1 s on its own in the interpreter, since `make test` runs every test of the project there and two tests of 55 s each once took two thirds of it: time a new or changed test by `check --test file.u:name` before committing it, and one that needs more, e.g. by loading the library, a project file, or a whole package, loads less, by a text, a fixture, or the cut load of imports (under Modules of `doc/implementation.md`), or moves to a directory that `project.u` runs only compiled. A test that parses a text takes `parse_text_recovering` of `ulang/parse/parse.u`, which reads no files and parses with `builtin_notation` of `ulang/syntax/notation.u`, so the text declares the other operators it uses, as `ulang/test/format/comments.u` does; `parse_file_text` of `ulang/parse/parse.u` loads the package of its path with the library, about 13 s per call in the interpreter, which two such tests took of `make test`.
- A test expects an exception by `assert raises p do … end`, in the file of its feature, and one whose parts it computes by a guard, `assert raises OsError(text) if text == "closed listener " ++ path do … end`. No file fails: an error that a phase must raise is a case, the lines of a source text in a test of `ulang/test/errors/`, one file per kind, `parse.u`, `types.u`, `assignment.u`, `matches.u`, `runtime.u` (failed assertions, uncaught exceptions, and the errors of the evaluator), `modules.u`, and `lemmas.u` (lemmas that the default proof leaves open, and those whose tests fail, by `run_text`), which runs the case through the phases by `check_text`, `run_text`, or `prove_text` of `ulang/test/cases/cases.u` and expects by `assert raises` the exception of the phase where it fails, `ParseError` or `ImportError` of `ulang/parse/parse.u`, `Located` of `ulang/check/check.u`, `Unformatted` of `ulang/format/format.u`, the `RuntimeError` of `ulang/syntax/error.u`, or `OpenLemma` of `ulang/prove/lemma.u`, with `_` for the parts that hold types, where an error that the tree lost is an `Unexpected` (under ulang/test of `doc/implementation-notes.md`). A case sits at a path of `ulang/test/errors/`, so it imports the helper packages of the project from their files; a case of several modules of one package gives their texts to `check_texts` or `run_texts`, which parse them by `parse_texts` of `ulang/parse/parse.u`, so that no package on disk fails, also for cycles and broken siblings. The cases each load the library, too slowly for the interpreter, so `project.u` runs `ulang/test/errors/` only compiled, by `make testc`, after asking, whose suite runs them alone by `out/suite/suite.sh ulang/test/errors`. The texts of the messages are tested apart, by `messages` of `ulang/check/message.u` and `ulang/syntax/error.u`; a hint of `hint_of` of `ulang/check/message.u` is no `Hinted` of `ulang/check/check.u`, so a case reads such a hint by `located_message` of `ulang/check/message.u`, and the message of `OpenLemma` of a gap ends with ` at L.C`. A single case runs in the interpreter too, `check --test ulang/test/errors/types.u:<name>`, since only the walk of `check --test` skips the directory, but slowly, since it loads its whole file, 1.5 to 3.5 minutes on a loaded machine.
- Tests of modules follow the packages: a directory is one package, so a test that is a module, or that expects an error in the sections of a module, has a directory of its own with the siblings it needs, e.g. `ulang/test/modules/siblings/`, and a helper that tests import is a package of its own, imported by its path from the root, `import ulang.test.modules.hiding`. The directory of an imported package needs a name of letters, digits, and `_`, `notation_right/`, as does every name of a path that a qualified name writes, the file of the module included: as in Java, `-` is no part of a name, since it is an operator, so `own-int.Int` reads as a subtraction, and a module of a file or directory with `-` cannot be qualified, which the files of programs and the cases of `ulang/test/errors/` with their ids such as `ulang/test/errors/own-type-clash` do not need.
- `checks/` holds the checks of the repository, programs whose `main` runs compiled at the root, since they parse the sources of the compiler, which the interpreter does too slowly, while their tests are of their own functions and run as all others do; `make testdocs` builds and runs them, after asking. `checks/docs.u` checks that each reference of `CLAUDE.md`, `README.md`, the files of `doc/`, and the files of `ideas/`, a list of names in backticks, separated by commas, `and`, or `or`, then `of` and a file, names declarations of that file, so lists of other things are separated by `;`, and a name that is only planned is written with `in`, not `of`. A list of names is read backwards from `of`, each name before a separator, so a word between two names that is no separator ends it: "by default `main`, `EntryProc` of …" names `main` in that file. It also checks that the keywords that `doc/language.md` lists are those of `keywords` of `ulang/parse/lex.u`, by `keyword_problems` of `checks/docs.u`, and runs each fenced block of the language u in `doc/language.md` as a case of `run_text` of `ulang/test/cases/cases.u`, a formatted file whose tests pass (`block_problems` of `checks/docs.u`), while blocks without `u` are fragments, and that no comment of a `.u` file of the project writes a container in a form that ulang no longer has, names of a list in brackets not after a name, of a set or a map in braces, or of an array between bars, where one name in brackets counts only as the argument of a call, since comments also cite other languages (`old_forms` and `comment_problems` of `checks/docs.u`).
- Take the expected exception of a case from a run of it, never guess it, e.g. by a pattern that matches nothing, such as `OsError("?")`, so that the exception is raised further and shows its value; positions count in the text of the case, which must be formatted if it parses and checks. A case of a bug that depends on an order, of names or of declarations, is checked against the code before the fix, since it may pass without it.

# Language

## Writing ulang

`doc/language.md` is the language for writers of programs, by example: its principles, the habits of other languages that fail, the constructs, the semantics of effects and exceptions, and the library with its shared names; read it before writing ulang. The errors give the form to write after `; ` for the habits that they recognize (`hint_at` and `operator_hint` of `ulang/parse/parse.u`, `hint_of` of `ulang/check/message.u`, and `Hinted` of `ulang/check/check.u`, with the cases `habits` of `ulang/test/errors/parse.u` and `hints` of `ulang/test/errors/types.u`). The habits of other languages that fail, which `doc/language.md` gives with more:

- Statements are `let x := e` of a name bound once, `var x := e` of a variable, `x := e` of an assignment, whose commas are sequential, `a := 1, b := a`, `p(in a, out b)` of a call, also `p(in a, out _)`, which drops the out, `raise e`, `skip`, and the blocks, where `let` and `var` stand anywhere in a body, up to its end, and a `let` is assigned by nothing, so `x := 1` of a `let` is `x is not assignable`; no `return`, `break`, or `+=`, so a procedure gives results by its `out` formals, and a loop ends by its condition or an exception.
- The keywords that `doc/language.md` lists are no names, also not of fields, formals, or locals; `and`, `or`, `not`, `show`, and `compare` are names, and the forms `List`, `Set`, `Map`, and `Array` are names of types, forms only before `(`.
- `if c then … end` and `while c do … end` in statements, `if c then a else b` in expressions, which always has its `else`; `else if` opens an `if` of its own, with its own `end`, and no `elif`; a missing `end` is reported at the construct still open where the parse ends, `the if, or a construct inside it, has no end`, which may be at the end of the input (`expect_end` of `ulang/parse/parse.u`).
- Cases with the same body share one head, `case TPlus | TMinus =>`, also nested, `Some(1 | 2)`, where every alternative binds the same variables; `||` is no operator, Bool has `and`, `or`, and `not`.
- Containers are forms, `List(1, 2)`, `List(x; rest)` also in patterns, `Set(…)`, `Map(k => v)`, `Array(…)`, never `[1, 2]` or `x :: rest`; `[…]` is only for type arguments, `List[Int]`.
- Tuple types are written as tuples are, `(Int, Str)`, also as type arguments, `List[(Int, Str)]`, and `()`; since `(A, B) -> C` is a function of two arguments, a function of one pair is `((A, B)) -> C` (`as_type` and `type_apply` of `ulang/parse/parse.u`).
- Strings join by `++`, never `+`, which is of `Int` only, and `show` gives the text of any value.
- `//` starts a comment to the end of the line, anywhere, which `format` keeps where it stands: on a line of its own above the next part, at the indentation of that part, or at the end of the line of the part before it; one that the layout of its part has no place for, such as inside an operand, moves above the line of the part. The doc of a declaration is the run of comments right above it.
- Functions are expressions without `raise`, failing only by the exceptions of builtins, so code that raises, may not terminate, or reads files is a procedure.
- An exported procedure that raises says so after its formals, `procedure load(in path: Str, out text: Str) raises OsError, ParseError`, in `export` and `implementation` alike, and a formal of a procedure type says what its values may raise, `step: (in Int, out Int) raises Failed`, and so does an entry, a procedure without formals such as `procedure main() raises OsError`, so that no checked exception escapes a run that its raises do not declare; private procedures with formals infer it, so the errors name each place to change: `p raises T, which its raises omit` at the raise or call, `the procedure value q raises T, which its type omits` where `q` is passed, and `the handler of T is unreachable` for a handler that nothing in its `try` can reach.
- Layout is not written by hand: `ulang.sh format` gives it, and `check` rejects any other.

Check after each small edit; which declaration an overloaded name such as `size` takes depends on the imports and the types, so read the `export` sections of the imported packages. Within one module a name is overloaded only by arity, so a `lower(s: Str): Str` beside a `lower(c: Char): Char` is no overload, and `refactor @put` of it replaces the other; and `get(k, xs)` of a list looks up an association list, while `at(i, xs)` takes the element at an index.

# Style

## Names

- Formals are the parameters of functions, procedures, and lambdas; params are type parameters.
- Functions, procedures, and locals are snake_case, e.g. `zonk_type`; constructors and types are CamelCase, e.g. `TSort`, `TypeError`.
- Names are descriptive but short, and one concept has one name, without short and long forms, for types, functions, and variables alike: `Constr`, `Mod`, `Sig`, `Prog`, not `Constructor`, `Module`, `Ctx`, `Program`, and a variable `constr` never has a `constructor` next to it.
- Variables are named by their type: `toks`/`tok`, `cmds`/`cmd`, `sig`, `loader`, `run`, `typ` and `types`, `fun`/`funs`, `text` for source and `offset` for positions in it, `name` for an `Id`, `cases`, `cond`, `body`, `prec`, `constr`/`constrs`, `field`/`fields`, `prog`, `expr`/`exprs`, `pat`/`pats`; `i`, `j` for plain counters.
- A variable of type `Stmt` is `stmt`, unless the declaration has another statement of that name, e.g. a pattern of `EProc` or `CProc`; parts of a statement keep their roles, `body`, `loop`, `step`.
- Patterns bind the names of the fields they match, `case EField(base, field)`, so a field is named by its role and a variable around the match by its type; where both would clash, the field name is the one to improve.
- Names carry no numeric indices, e.g. `stmt1` or `e1`: two of a kind in one scope get names by their roles, e.g. `decl` for the record of a constructor where a pattern binds `constr`, and a clash is resolved by a better name for one of them. Two conventions name the rest: what the checker makes of a part has the prefix `typed_` before the name of the part's field, `typed_expr`, `typed_pat`, `typed_guard`, `typed_args`, as `expr_branches` of `ulang/check/check.u` binds them; and the second of a pair without roles of their own has the suffix `_`, the tails `xs_` and `ys_` of two lists matched together, the types `t` and `t_` of `unify`, or the signature `params_` and `formals_` of a definition against `params` and `formals` of its export in `check_signatures`. Renaming never makes a short name long, e.g. `t` to `candidate`.
- Procedures that consume tokens start with `parse_`, except `advance` and `expect`; functions that build trees do not. Predicates on the next token are `at_X`, grouped together.
- Predicates, functions to `Bool`, are `is_X` for a property, `is_useful`, `has_X` for a part, `has_holes`, a verb in the third person for a relation, `contains`, `covers`, `occurs`, and `at_X` for the next token, never a bare adjective or noun such as `useful` or `holes`.
- `show` is text that parses back literally, never `show_X`; `format_X` prints into another language, e.g. types, values, tokens, programs, or C as source.
- Pattern aliases name a shape at the level where code works with it, by the prefix of that level, `VInt(n)` of values in `ulang/run/run.u`, `PCons(head, tail)` of patterns, `ECall(name, typ, args)` of expressions, `TBool()` of types, `HTuple()` of heads, and not names, so no guard such as `if constr == cons_name()`; they always build as well as match, so none has `_`, except the aliases of alternatives that name a group of constructors by a definition, such as `CNoCode` and `CNoSpec` of `ulang/syntax/syntax.u`, which only match, stand for a group where every site treats its members alike, and which a new constructor joins only if it fits the definition; and a type inside, as of `Var`, is a formal, `_` where matched and `THole` where built. Aliases over names that checking resolves, such as `PNil()` and `ENil(typ)` of `ulang/syntax/builtins.u`, match only checked code; unresolved names, as the parser writes them, are matched directly, `PApp(Name(List(), "Nil"), List())`, where a constructor written bare, `case None =>`, is a `PVar` that the checker resolves and `None()` a `PApp`, so a test of the source takes both. Functions such as `nil_name()` remain where a `Name` is used on its own.

## Docs and examples

- Docs state what the code and its names do not: a rule, a reason, or a convention that holds beyond the line, e.g. that a position is in another module, or in which order a function visits. Omit those that restate the name of a declaration or the lines below. Name a piece of code by a function instead of commenting it, and put a note on the statement, `case`, or command that it explains.
- A function whose name and types leave its meaning open, such as the order of its arguments or what it does at the edges, has an example, exported or private, on the first occurrence of its signature, `example slice("abcd", 1, 3) == "bc"`, which, unlike a doc, cannot go stale. An example applies its own function to arguments of the types of its signature, since an overloaded name may otherwise take another declaration, which the checker does not catch.

## Code

- Functions only for computations that terminate; code that may not terminate, such as the evaluator of `ulang/run/run.u`, is written as procedures, unchecked.
- Records over positional tuples for anything kept in a table or passed on, with fields named by role, which uses read as selectors, `sc.typ`, `proc.ins`; tuples for pairs that are built and taken apart at once. A datatype of one constructor is named as its type, `Sig`, `Scheme`; the alternatives of a sum have the prefix of their datatype, `CFun` of `Cmd`; separate records of one family share a suffix, `ProcSig` and `ConstrSig` of `Sig` (`ulang/check/sig.u`), `FunDef`, `ProcDef`, and `ConstrDef` of `Defs` (`ulang/check/defs.u`).
- Patterns have two printers: `format_pat` of checked patterns, for messages, and `format_pattern(notation, …)` of the source, which alone keeps the round trip of `format`.
- The notation is threaded as the first parameter where it is needed, not bundled into records.
- A match names the constructors where a new one would need a decision, e.g. a traversal, with `|` where they share a body, `case THole | TMeta(_) | TParam(_) =>`, for every datatype alike, so that the exhaustiveness check lists each place to change. A catch-all `_` stays where every other constructor means the same: a predicate or a selector of one or two constructors, a dispatch on the next token whose `_` is the parse error of everything else, a match over the many constructors of `TypeError` that treats a few of them apart, and a match where another place decides, as `enter_section` of `ulang/parse/parse.u` does what a section holds. A constructor that an earlier phase rules out gets a case of its own, which in a procedure raises `Unexpected` or another `InternalError` of `ulang/syntax/error.u`, and in a function, which cannot raise, gives the value of the other cases, with a doc of the phase that rules it out, as `exposed` of `ulang/check/check.u` does.
- Write recursions with a large `match` explicitly, not as `foldl` with a step function; folds are for small steps.
- Each local is declared where it is first needed, in the innermost body that uses it, a case of a `match` or a branch of an `if`, and in each case that uses it, so that a reader sees which case uses which local, and by `let` unless something assigns it later (`UnassignedVar` of `ulang/lint/lint.u`).
- In traversals such as `ulang/prove/simp.u`, bind every result of a recursive call by `let` before using it, keep the recursion in the traversal (`simp_term`), which passes the simplified parts to one helper per kind of term (`simp_app`, `simp_ite`) that only combines them.
- Iterate a map by `for k => v in m`, not by first making a list of its entries, `List(for x in m)`, and then taking the pairs apart; `for (k, v) in c` is for a list of pairs. This was mistaken for `for (k, v) in m` when flattening `field_table_decls` of `ulang/compile/compile.u`.

## Layout

- Code is 80 columns wide, while comments are filled to 120, which the warning of `refactor` on long comment lines takes, a convention that `ulang/format/format.u` does not state.
- Signatures that do not fit on one line have one parameter per line, with `in  ` padded so that names align with `out ` and `ref `.
- The printer (`format`) lays out `match` and `catch` by one rule: each case body starts on the line after `=>`, and a blank line separates the cases unless there are at most two and each has a head and one line of body (`case_chain` of `ulang/format/format.u`); a `List(…)`, `Set(…)`, `Map(…)`, or `Array(…)` wider than 80 characters has one element per line, also a `List(…)` in a pattern, and so has a procedure head that is wider, with the modes `in`, `out`, and `ref` in front of the first formal of their group; the body of a function and the pattern of a pattern alias start on the line after `:=`, and the body of a `let` on the line after `in`, at the indentation of the line of the `let`; `if … then … else …` in expressions stays on one line if it fits in 80 characters, else each branch has a line of its own, one deeper, with `else if` at the level of the first `if` (`ite_text` and `spread_ite` of `ulang/format/format.u`).
