# ulang

A minimal language with pure functional expressions, imperative statements, datatypes, and Hindley-Milner inference, implemented in itself in `ulang/`: parser, checker, interpreter, and a compiler to C, with a runtime in C (`ulang/runtime/`). The Scala 3 implementation it started from is on the branch `scala-baseline`.

## Working rules

- A question asks for an answer, not an action: answer it, propose what suggests itself, and act only on an explicit go-ahead. Read-only lookups are fine.
- Checks:
  - After a refactor that keeps behaviour, `out/ulang.bin check ulang/ulang.u` is enough.
  - Run `make test` after changes of behaviour or when asked, and say that it ran; after edits of tests, rerun only the affected files.
  - `make testc` only with a strong reason, e.g. changes to `ulang/compile.u`, the runtime, or what the generated C depends on, and only after asking.
  - Time every phase of a run of checks and keep the output, so that questions about durations are answered from it; never rerun only to measure.
  - Redirect the output of `make` to a file, never pipe it into a command that may exit first, such as `tail -0` or `head`: `make` then dies of the broken pipe before linking, and a stale `out/ulang.bin` runs the next checks.
- Commits: no `Co-Authored-By` for Claude; end the message with `Agentic Coding (<model>)`, e.g. `Agentic Coding (Claude Opus 5.5)`. Run `make` after every commit, so that `out/ulang.bin` is current.
- Other sessions may edit the same files, also `TODO.md` and `CLAUDE.md`, at the same time: commit only the hunks of your own work, applied to the committed version, and leave theirs in the working tree.
- `TODO.md` holds open items only, each as the problem and the desired solution; delete an item when it is done. Explanations go into this file or `README.md`.
- Plans and guides of work in progress, such as `packages.md`, are files at the root that are not versioned: add each to the section of notes of `.gitignore` while it is in use, and remove it there with the file when the work is done; what stays true afterwards goes into this file, `README.md`, or `TODO.md`.
- When working on ulang code, record in `unclear.md` each trip-up and unclear point: a wrong guess, a search that led nowhere, a doc that was stale or misleading, each as what was wrong and what is so, so that the documentation can be fixed from it.
- To compare a compiler before and after a change, e.g. the C that both compile from the same files, build the one before from the committed sources in a worktree of its own, never take the `out/ulang.bin` of the main tree, which other sessions rebuild from their uncommitted edits; the binary finds the library by the path that `-DULANG_LIB` compiled in, no variable of the environment, so its worktree stays until the comparison is done.
- Profile compiled programs with gprof, not perf, which cannot record call graphs here: build with `-pg`, run with `GLIBC_TUNABLES=glibc.gmon.maxarcs=50000000:glibc.gmon.minarcs=1000000`, and sum several runs by `gprof -s` if one has too few samples; gprof does not see time in shared libraries such as libgc.

## Build

- `make` builds the tool `out/ulang.bin`, the compiler of the current sources `ulang/*.u` and `prelude/*.u`: the seed `bootstrap/ulang.bin`, built from `bootstrap/ulang.c`, the C of the last compiler that compiled itself to the same C, translates them to `out/ulang.c`. Each binary is linked with the runtime, GMP, and the Boehm collector, and rebuilt when its inputs change: about 15 seconds from nothing, 7 after an edit of the sources; `rm -rf out` loses nothing that `make` cannot rebuild. `ULANG_LIB` is the directory `prelude/` of the library, for imports and `os_library`. Commands exit with status 1 if anything fails, and need `ulimit -s unlimited`, which the Makefile sets.
  - `ulang.bin run <file> [<procedure>] [-- args]` calls the procedure, by default `main`, without parameters, in the interpreter `ulang/run.u`; `os_args` gives the arguments after `--`.
  - `ulang.bin test <file> [<name> …] [-- args]` runs all or the named `test`s, each on its own, printing `test name passed` or `test name failed: …`.
  - `ulang.bin test <dir> [<path> …]` runs the `.u` files below the directories, in the order of names, and the given files, each in its directory with all its tests in one process. A file must succeed, or fail with the error that its first line states; it prints the files that do not, and `N of M files passed`.
  - `ulang.bin check <file>` only checks.
  - `ulang.bin compile <file> <entry> <target.c>` translates to C, whose `main()` calls the procedure `entry`, or runs all tests for the entry `test`; compile it by `cc -DULANG_LIB='"'$PWD/prelude'"' -I ulang/runtime target.c ulang/runtime/ulang.c -lgmp -lgc`.
  - `ulang.bin format <file>` prints the file as source (`format_program` of `ulang/format.u`), and fails if that does not parse to the same commands.
  - Parse errors are reported at their token, type errors at their declaration, as `at L.C` after the message, with ` in m` for a module `m` other than the file, of an imported package or a sibling (`ImportError` of `ulang/parse.u`, `Located` of `ulang/check.u`). Compile and runtime errors have no positions; the texts of the runtime errors that both backends report are `runtime_message` of `RuntimeError` in `ulang/error.u`, which `ulang/compile.u` writes into every program as the formats `u_text_*` that the runtime prints; `InternalError` of `ulang/run.u` holds the errors of the interpreter that checked programs never raise.
- The repository is one project, whose root has `project.u`, so that the modules of `ulang/`, `prove/`, and `tests/` are known by their paths from it, and tests import their helpers by such paths.
- `make selfcompile` compiles the sources with `out/ulang.bin`, and `make bootstrap` with the interpreter of the seed (`bootstrap/ulang.bin run ulang/ulang.u main -- compile …`), for sources that the seed cannot compile. Both replace the seed, `bootstrap/ulang.c` and `bootstrap/ulang.bin`, only if the new compiler compiles itself to the same C, keep the previous pair in `bootstrap/<time stamp>/`, and then rebuild `out/ulang.bin`. Their stages are in a directory `out/stage-*` of each run, removed if it succeeds. The C of the seed is versioned, the binaries are not, and of the backups only those worth keeping are committed. `make selfcompile` takes about 15 seconds, `make bootstrap` about 4 minutes.
- `make test` is `out/ulang.bin test tests ulang prove prelude`, about 23 seconds, since each file of `ulang/` loads and checks the whole package of the compiler.
- `make testformat` formats every file that parses, testing parser and printer by their round trip.
- `make testc` (`testc.sh`) runs the same files compiled, with the entry `test`, by `cc -O2` and the runtime object `out/testc/ulang.o`, in parallel, about 100 seconds. `compile` loads the whole library for every file, so also the module `list`, which the runtime needs.
- `make install` packages the VS Code extension of `vscode/` as `ulang.vsix` into VSCodium: highlighting, a run button, `▶ Run` links above procedures without parameters and tests, errors in the Problems view, and tests in the Testing view, by running the `out/ulang.bin` of the workspace or of the setting `ulang.binary`, so after a change of its path, `make install` again.

## Tests

- Tests are end-to-end only: programs in `tests/` with named tests `test name() := …` of `assert` statements. Names are distinct, and the parser accepts formals, which the checker rejects. Programs are entered by procedures without parameters, e.g. `procedure main() := …`.
- A file expected to fail states the error in its first line, e.g. `// type error: unknown variable x at 3.1`. They sit in the subdirectories of `tests/errors/` by kind of error.
- Tests of modules follow the packages: a directory is one package, so a test that is a module, or that expects an error in the sections of a module, has a directory of its own with the siblings it needs, e.g. `tests/errors/modules/ambiguous-name/`, and a helper that tests import is a package of its own, imported by its path from the root, `import "tests/errors/modules/hiding"`. The directory of an imported package needs a name of letters, digits, and `_`, `notation_right/`, while directories that nothing imports may have `-`. A helper whose own error is expected states it in its first line too, as `tests/errors/modules/broken/broken.u` does.
- Take the expected message and position of an error test from a run of it, never guess them; `format` puts a blank line after the first line, so positions count in the formatted file.

## Modules

- The root of a project is the nearest directory above a file with `project.u`, else the file's own directory, and a module of a project is known by its path from the root without `.u`, e.g. `ulang/check`, which messages, ` in m`, and mangled C names show; the modules of the library, a directory with `prelude.u`, as members of the package `prelude`, e.g. `prelude/map` (`place_of` of `ulang/parse.u`, `library_module` of `ulang/syntax.u`), except in C, where they keep the names of their files, e.g. `t_list_46_List` and the key `"os.OsError"`, as the runtime and the seed refer to them (`c_text` of `ulang/compile.u`). `import "p"` loads the package of the directory `p` from the root, once, without the tests of its members, where the names of the path have letters, digits, and `_`, also keywords, and never occur as tokens, so no `..` and no `-`; an import of a file `….u`, of an unknown package or one without members, of the own package, of the library, which every module sees without importing it, and a cycle of packages are parse errors (`parse_import` and `import_package` of `ulang/parse.u`). Programs cannot be imported. `Mod.imports` are the ids of the imported packages, which `seen_modules` of `ulang/syntax.u` expands to their members. The parser gives `Source(mods, packages, main)` of `ulang/syntax.u`, the modules in load order, each after its imports, as `Mod(name, imports, exported, builtins, implemented)` with the commands of its sections paired with their positions, and the packages as `Package(id, members)`. Its only state is the source loaded so far, from which each module gets its initial notation, the exported notation of its imports and of the other members of its package (`exported_notation` of `ulang/notation.u`, `exported_ops` of `ulang/parse.u`).
- Packages: a file with sections is a member of the package of its directory, known by the directory from the root, and `prelude` for the library; `project.u` and files without sections, programs, are none. Loading a module loads its package, all members, each parsed with the notations that the export sections of the others declare, read from their tokens before they are parsed, where whether a file has sections is known from its text, by a line that starts with `export`, `builtin`, or `implementation` (`load_package`, `has_sections`, `load_program` of `ulang/parse.u`). Members see each other's exports without imports, also cyclically, and overload each other by type, while their private declarations and the constructors and fields of their abstract types stay private to their file; a program sees the exports of the package of its directory. Programs are not imported: each is the main file of its run, loaded after the package of its directory (`load_program`); so packages are the only units of imports, and cycles are cycles of packages. A project with a directory `prelude/` at its root shares the ids of the library, which `import "prelude"` rejects, and clashes with it in C.
- Every module implicitly imports the whole library, the package `prelude` of `prelude`, `option`, `list`, `str`, `set`, `map`, `array`, `buffer`, and `os`, whose members see each other (`library_modules` and `implicit_imports` of `ulang/syntax.u`), so no module imports one; a module may declare their types again, which hide those of the library, and their functions with other types or arities, which overload them.
- A module sees its own declarations, the exported ones of the members of the packages it imports and of its own package, and the prelude, and likewise for notations: imports are not transitive. The checker resolves every name to its module, and checks the members of each package together, and each program alone, once, after their imports, against their signatures (`check_program` and `check_package` of `ulang/check.u`, `Sig` of `ulang/sig.u`), where the private declarations of the members are in the signature, hidden from the other members by `State.hidden` and `State.hidden_sorts`, and type aliases are declared each after those it names.
- Sections, see `prelude/set.u`: imports, then `export` with notations, datatypes, aliases, signatures without bodies, and abstract types `type T[A]`, then optionally `builtin`, then `implementation` with definitions that repeat the signatures exactly, `data` for the abstract types, private declarations, and tests. Other modules see neither the private declarations nor the constructors and fields of abstract types. A module without sections has all its commands implemented and exports nothing, so only main programs have no sections; their private procedures and tests are the entry points of `run` and `test`.
- A `builtin` section has exported signatures without definitions and types without a definition, `type T[A]`, which the interpreter (`builtin_names` of `ulang/run.u`) and the runtime (`builtin_functions` and `proc_name` of `ulang/compile.u`) define, make, order, compare, and show; its uses keep their module, and no `compare` or `==` is synthesized for its types. Examples: `str.u`, `os.u`, `array.u`, and the prelude, whose builtin section declares `Bool`, `Int`, `Str`, `Char`, the arithmetic `+`, `-`, `*`, `/`, `%`, and `++` of strings.

## Library

- The prelude declares the operators, `abs`, `gcd`, `first` and `second` of pairs, and the exceptions of builtins: `DivisionByZero` of `/` and `%`; `OutOfBounds(Int, Int)`, index and size, of `at` and the strict `slice` of strings and arrays and of `put` of arrays; `NoCharacter(Int)` of `chr`; `MissingField(Str)` with the name `T.f`; and `Unordered(Str)` and `Incomparable(Str)` with the name of a type.
- `<`, `==`, `compare`, `show`, `and`, and `or` are builtins without a module. `compare` is a total order of all values, consistent with `==`, with results `-1`, `0`, `1`, where constructors are ordered by their position in their declaration; `<`, and the `<=`, `>`, `>=` of the prelude, each by one `<`, follow it.
- `str`: `chars(s)`, `str(cs)`, `ord`, `chr`, `is_digit`, `is_letter`, `is_space`, `size`, `at(i, s)`, `get(i, s)` as an option, `contains(c, s)`, `slice`, `starts_with`, `ends_with`, `join`, `split`, `quote`, `number`.
  - A `Char` is a Unicode code point, 0 to 0x10FFFF without the surrogates 0xD800 to 0xDFFF, else `chr` raises `NoCharacter`, and a `Str` a sequence of them, which `size`, `at`, and `slice` count; `is_letter` and `is_digit` are ASCII, as names are. UTF-8 is only the encoding of the system: the procedures of `os` decode files, arguments, and names of files, where invalid UTF-8 raises `OsError`, and encode what they write.
  - The runtime stores each string in units of 1, 2, or 4 bytes, the narrowest that holds its code points, so that equal strings have equal units (`u_str_at` of `ulang/runtime/ulang.h`); literals are `U_LIT` of `"…"`, `u"…"`, or `U"…"` by their greatest code point (`format_str` of `ulang/c.u`).
- `map` and `set`: `Map[K, V]` and `Set[A]`, abstract types of AVL trees ordered by `compare`, with `compare` and `==` by their elements and entries; `intersect(s, t)` of sets.
- `buffer`: `Buffer[A]`, the elements of a loop that adds at the end, kept as the reversed list: `empty()`, `b ++ xs` for a list `xs`, `size`, and the folds in the order of adding, so `list(for x in b)` reads it out; lexer, parser, and loops of the checker and the compiler use it where a list grows with the program, and `++` of lists where it is bounded by a construct.
- `array`: immutable `Array[A]`, kept as `VArr` of `Value` in `ulang/run.u`: `from_list(xs)`, `size`, `at(i, a)`, `get(i, a)`, `slice`, `contains`, and the folds.
- Lists, sets, maps, arrays, and strings share names and orders of arguments:
  - `size`, `contains`, `get` (of association lists for `list`), `remove` (elements of lists and sets, keys of maps), `empty` of sets and maps, `exists(c, p)`, `forall(c, p)`, and the folds `foldr(c, acc, f)` and `foldl(c, acc, f)`, in the order of lists and ascending for sets and maps, where `f` and `p` of maps take key and value.
  - Conversions are forms, `list(for x in c)` of the elements in order, `list(for k => v in m)` of the entries, `set(for x in xs)`, `map(for (k, v) in ps)`, where the last entry of a key counts, `array(for x in xs)`, and `str(cs)` of characters.
  - `infix right 8 ++` and `infix left 7 --`: `++` concatenates lists and strings, unites sets, and joins maps, where the entries of the second count; `--` removes the elements of a list or set, and the keys of a set from a map.
- `os` declares `OsError` and the builtin procedures `os_args`, `os_read`, `os_write`, `os_library`, `os_print`, `os_print_error`, `os_exit`, `os_list` (sorted entries with whether each is a directory, without following links), `os_is_dir`, `os_cwd`, and `os_chdir`, which raise `OsError` when they fail on files, with `os_walk` of `os.u` for the files below a directory and `os_println`, which prints a string by `os_print` and then a newline, while `os_print` prints it as it is, and relative paths start from the working directory.

## Overloading

- The candidates of a name are its declarations in all visible modules, its own module's no more than the others; locals hide them all, the parser builds no qualified names, and within a module, overloading is only by arity. Declared hooks `show`, `compare`, and `==` are no candidates: uses take the builtins, which reach the hooks through the types of their arguments (`is_hook` of `ulang/check.u`).
- An applied name infers its arguments first, then keeps the candidates of its arity whose instance unifies with them and the expected type, each tried on a copy of the substitution. One remaining candidate is committed; with several, the use gets a fresh type, a placeholder name, and a pending entry.
- Pending entries are solved to a fixpoint at the end of the command, before `zonk` replaces the placeholders, and lets do not generalize their types. A use resolves uniquely, by its types alone, without preferences: since the substitution only grows, a candidate that does not fit never fits again, so a use with one candidate left is committed, whatever the order of solving, e.g. `map.put` of a map literal, which then fixes the type of its `map.empty` when `set` and `array` are imported too. No candidate is an error, and several at the end of the command are ambiguous, both listing the candidates with their types.
- Accesses `e.f` and updates `e with f := a` resolve by the type of `e`, which must be known when the checker reaches them, else `UnknownFieldOwner`. Lambdas that are arguments wait until the other arguments and the function type are known, and then take the types of their formals from it, so `exists(xs, lambda q => q.x == 3)` and `(lambda p => p.x)(Point(1, 2))` check (`infers_first` and `infers_lambdas` of `ulang/check.u`); a lambda that is bound by a `let` has no expected type, while the declared type of a local, an assignment, or a result gives one, `local g: Point -> Int := lambda p => p.x`.

## Syntax and translations

- A datatype declares each of its constructors after `case`, as a match over it has its cases: `data T[A] := case C(name: A) case D`, one per line. Every argument of a constructor is a named field, `C(name: T, …)`; a name may repeat in the constructors of a datatype with the same type, and patterns bind the variables of the fields' names where they can. Fields give accessors `e.name` and updates `e with name := a, other := b`, parsed as `EField` and `EUpdate` (from the left) and resolved by the type of `e` to the accessor `T.name` and the updater `T.name:=`, so that checked programs have neither, which raise `MissingField("T.name")` for constructors without the field. The checker declares both for each field of a datatype, without definitions (`declare_fields` of `ulang/check.u`), exported where the constructors are, and the interpreter and the compiled code implement them by the position of the field in each constructor (`fields` of `Defs`, `u_select` and `u_update` of the runtime, or `u_field` where all constructors have the field at the same position). A comma followed by `name :=` continues the updates, also in `assign` and `local`.
- The forms `list(…)`, `set(…)`, `map(…)`, and `array(…)`, whose keywords are reserved, build containers (`parse_form` of `ulang/parse.u`, `EForm` and `EFor` of `ulang/syntax.u`):
  - `list(a, b)`, `list(a, b; r)`, `list()`; `set(a, b)`; `map(k => v, l => w)`; `array(a, b)`; the rest `r` after `;` is the container that the elements are added to, where the new entries of a map win, and arrays have no rest. In patterns only `list(x, y; rest)` and `list()` occur, the constructors `Cons` and `Nil`, which are also written so.
  - `list(for p in c if q yield e)` and the like, with generators `for p in c` and `for k => v in m` and guards `if q` from left to right, where `yield` is omitted after exactly one generator, which yields what its pattern binds, `set(for x in xs)`, `map(for k => v in m if q)`. Patterns of generators are irrefutable, else the translation is a type error.
  - The checker translates them (`generator` and `fold_expr` of `ulang/check.u`): a literal is unrolled, `set(a, b)` is `set.insert(a, set.insert(b, set.empty()))`, `map(k => v)` `map.put(k, v, map.empty())`, `list(a; r)` is `Cons(a, r)`, and `array(…)` is `array.from_list` of a list; a generator infers its container, solves, and takes `foldr` for lists and `foldl` for the others from the module of its type, with the formals typed by the type arguments of the container, so `x.f` works in the next generators; a generator over a map with one pattern binds the pair, and an unknown type is `UnknownContainer`. The accumulator has a name that users cannot write.
  - `show` writes the forms, `list(1, 2)`, `set(1, 2)`, `map(1 => "a")`, `array(1, 2)`.
- `for p in c if q do … end` is a statement over the elements of any container in the order of its fold; the parser makes of it a block, the pattern alias `ForBlock` of `ulang/syntax.u`, which collects `list(for item in c)` and loops by `while` and `match`, so its body assigns the variables around it, and which the printer matches to read the block back (`parse_for` of `ulang/parse.u`, `for_parts` of `ulang/format.u`). Its pattern is irrefutable like those of generators, else the exhaustiveness check of the `match` rejects it.
- `if` always nests, without chains: in statements, `if c then … end` and `while c do … end` have a keyword after the condition, as `for p in c do … end` has, and `else if c then … end` is an `if` in the body of the `else`, with its own `end`, and statements may follow it there; in expressions, `if c then a else if d then b else e` nests the same way.
- Pattern aliases, `pattern And(a: Expr, b: Expr): Expr := EApp(EFun(Name(None, "and")), list(a, b))`, name a pattern whose variables are exactly the formals, each once (`AliasVariables`); `pattern` is a keyword, and an alias without formals is declared and built with `()`, `Zero()`, and matched also bare, `case Zero =>`. The checker types the pattern once in its module, after the constructors and the aliases before it, so aliases do not recur, and stores it with its constructors resolved in `Sig.pat_aliases` (`PatAlias` of `ulang/sig.u`, `declare_pat_aliases` of `ulang/check.u`); `binders` expands a use, which an alias joins as a candidate next to the constructors, by `subst_pat` of its arguments for the formals, so that exhaustiveness, `ulang/run.u`, and `ulang/compile.u` see only constructors, and errors show the expansion. An alias without `_` is also a function of its name, whose body is `pattern_expr` of the pattern (`definition_of`), so `And(x, y)` builds the value; one with `_` only matches (`PatternOnly`). Aliases share the namespace of constructors and functions; an alias in `export` is exported whole, with its pattern, and must not match private constructors (`PrivateConstructor`), and one in `implementation` is private. `format` prints the alias at its uses as written.
- The formals of function lambdas are patterns: `lambda p, q => e` with patterns that are not all variables is `lambda (1), (2) => match ((1), (2)) case (p, q) => e end`, checked for exhaustiveness as `let` is (`lambda_patterns` and `patterns_of_lambda` of `ulang/syntax.u`).
- `-n` for a number `n` is a negative literal, in expressions and patterns, e.g. `case -1 =>`.
- `let … in …` is an expression, not a statement, and the patterns of `let`, of generators, and of lambdas are irrefutable, so tests of refutable patterns, also of pattern aliases such as `And(a, _)`, use `match`.
- `ulang/compile.u` builds list comprehensions over lists and arrays, also of several generators, by nested loops without intermediate lists, array literals by `u_mk_array`, and array comprehensions by loops that fill an array sized by the first generator, grown for further generators and shrunk at the end unless it is exact.

- Comments are documentation, part of the syntax, and printed back by `format`: a run of `//` lines from the start of a line, with the indentation of the line below it and no blank line between, is the doc of what follows: of a command (`Top(pos, doc, cmd)` of `ulang/syntax.u`, the items of the sections), of a constructor of a datatype or a `case` of a `match` or `catch` (`Constr`, `Branch`, and `Catch`), and of the module if it comes first in the file and a blank line, an `import`, or `export` follows it (`Mod.doc`). The lexer gives `TDoc` (`lex_doc` of `ulang/lex.u`), the parser takes it before a command or a `case`, `doc` is the first field and `""` means none, and the printer writes it back (`doc_lines` and `indented_doc` of `ulang/format.u`). Each doc is the text of its lines without `//` and the space after it, joined by newlines. Docs are not checked and not compiled. Any other `//`, at the end of a line, in the middle of a body, or detached by a blank line, is a parse error at the `//` (`misplaced_comment` of `ulang/lex.u`); the first line of a file that is expected to fail is a doc as well.

## Semantics

- `raise e` is an expression of any type, and a failed `assert` cannot be caught.
- Effects on variables are atomic: a procedure works on copies of its outs and refs, which reach the caller only when it returns, and the handlers of a `try` see the variables as before it. Compiled code copies outs and refs in and out, and saves the variables that the body of a `try` assigns before its `setjmp`.
- No formal, local, pattern variable, or formal of a lambda hides a local around it (`HiddenLocal`, `unhidden` of `ulang/check.u`), while locals may hide declarations, which depend on the imports; the names of the translations, such as `(acc)` and `(item)`, nest.
- Variables are read only where they are assigned on every path, and outs must be assigned on every path that does not raise, where passing a ref reads it (`Local` of `ulang/check.u`, joining the paths of `if`, `match`, and `try`; a `while` may not run its body, and a handler starts from the variables before its `try`).
- Procedures are values of types `(in A, out B, ref C)`: declared ones by name, and `lambda in x, out y, ref z => statements end`, which sees the variables around it by their values and assigns only its own outs and refs. `call p(…)` calls a variable `p`, which hides a procedure `p`; compiled code calls through `u_call_proc` and the wrappers `wp_`.
- Functions without parameters are computed once, interpreted and compiled.
- Orders, equality, and show of datatypes:
  - A function `compare` or `==` of two values `T[A, …]` of a datatype `T` of its own module, with distinct type parameters, is the order or equality of `T` (`order_of` of `ulang/defs.u`), which the builtins `compare`, `==`, and `<` use for all values of `T`, also inside other values and in generic code; other datatypes compare structurally.
  - Only abstract types declare `==`; datatypes with visible constructors may declare `compare`, which must agree with structural equality, unchecked. With `compare` alone, `==` is `compare(a, b) == 0`.
  - For an abstract type without `compare`, the checker synthesizes a private `T.compare` that raises `Unordered`, and without `==` either, a `T.==`, both raising `Incomparable` (`tests/orders.u`, `tests/modules/modules.u`).
  - A function `show` of one value `T[A, …]` of a datatype `T` of its own module, with distinct type parameters and the result `Str`, is the show of `T`, which the builtin `show` uses for all values of `T`, also inside other values; otherwise `show` gives the text of a value, strings in quotes.
  - A function `show` of one value, or `compare` or `==` of two, must be a hook of these forms, else `MisshapenHook`, since uses do not reach it otherwise.
  - The runtime finds these through the type descriptor of each object (`struct u_type` of `ulang/runtime/ulang.h`, one `t_` per datatype, pointing to the declared functions or the structural ones), the interpreter through the maps of `Defs` of `ulang/defs.u` from datatypes to them.

## Style

- Formals are the parameters of functions, procedures, and lambdas; params are type parameters.
- Docs state what the code and its names do not: a rule, a reason, or a convention that holds beyond the line, e.g. that a position is in another module, or in which order a function visits. Omit those that restate the name of a declaration or the lines below. Name a piece of code by a function instead of commenting it, and put a note on a `case` or a command, not in the middle of a body.
- Functions only for computations that terminate; code that may not terminate, such as the evaluator of `ulang/run.u`, is written as procedures, unchecked.
- Functions, procedures, and locals are snake_case, e.g. `zonk_type`; constructors and types are CamelCase, e.g. `TSort`, `TypeError`.
- Records over positional tuples for anything kept in a table or passed on, with fields named by role, which uses read as selectors, `sc.typ`, `proc.ins`; tuples for pairs that are built and taken apart at once. A datatype of one constructor is named as its type, `Sig`, `Scheme`; the alternatives of a sum have the prefix of their datatype, `CFun` of `Cmd`; separate records of one family share a suffix, `ProcSig` and `ConstrSig` of `Sig` (`ulang/sig.u`), `FunDef`, `ProcDef`, and `ConstrDef` of `Defs` (`ulang/defs.u`).
- Names are descriptive but short, and one concept has one name, without short and long forms, for types, functions, and variables alike: `Constr`, `Mod`, `Sig`, `Prog`, not `Constructor`, `Module`, `Ctx`, `Program`, and a variable `constr` never has a `constructor` next to it.
- Variables are named by their type: `toks`/`tok`, `cmds`/`cmd`, `sig`, `loader`, `run`, `typ` and `types`, `fun`/`funs`, `text` for source and `offset` for positions in it, `name` for an `Id`, `cases`, `cond`, `body`, `prec`, `constr`/`constrs`, `field`/`fields`, `prog`, `expr`/`exprs`, `pat`/`pats`; `i`, `j` for plain counters.
- A variable of type `Stmt` is `stmt`, unless the declaration has another statement of that name, e.g. a pattern of `EProc` or `CProc`; parts of a statement keep their roles, `body`, `loop`, `step`.
- Patterns bind the names of the fields they match, `case EField(base, field)`, so a field is named by its role and a variable around the match by its type; where both would clash, the field name is the one to improve.
- Names carry no numeric indices, e.g. `stmt1` or `e1`: two of a kind in one scope get names by their roles, e.g. `decl` for the record of a constructor where a pattern binds `constr`, and a clash is resolved by a better name for one of them, not by a suffix. Renaming never makes a short name long, e.g. `t` to `candidate`.
- Procedures that consume tokens start with `parse_`, except `advance` and `expect`; functions that build trees do not. Predicates on the next token are `at_X`, grouped together.
- `show` is text that parses back literally, never `show_X`; `format_X` prints into another language, e.g. types, values, tokens, programs, or C as source.
- Pattern aliases name a shape at the level where code works with it, by the prefix of that level, `VInt(n)` of values in `ulang/run.u`, `PCons(head, tail)` of patterns, `ECall(name, typ, args)` of expressions, `TBool()` of types, `HTuple()` of heads, and not names, so no guard such as `if constr == cons_name()`; they always build as well as match, so none has `_`, and a type inside, as of `Var`, is a formal, `_` where matched and `THole` where built. Aliases over names that checking resolves, such as `PNil()` and `ENil(typ)` of `ulang/builtins.u`, match only checked code; unresolved names, as the parser writes them, are matched directly, `PApp(Name(None, "Nil"), list())`. Functions such as `nil_name()` remain where a `Name` is used on its own.
- Patterns have two printers: `format_pat` of checked patterns, for messages, and `format_pattern(notation, …)` of the source, which alone keeps the round trip of `format`.
- The notation is threaded as the first parameter where it is needed, not bundled into records.
- Signatures that do not fit on one line have one parameter per line, with `in  ` padded so that names align with `out ` and `ref `.
- Write recursions with a large `match` explicitly, not as `foldl` with a step function; folds are for small steps.
- In traversals such as `prove/simp.u`, bind every result of a recursive call by `let` before using it, keep the recursion in the traversal (`simp_expr`), which passes the simplified parts to one helper per kind of term (`simp_app`, `simp_ite`) that only combines them.
- Iterate a map by `for k => v in m`, not by first making a list of its entries, `list(for x in m)`, and then taking the pairs apart; `for (k, v) in c` is for a list of pairs. This was mistaken for `for (k, v) in m` when flattening `field_table_decls` of `ulang/compile.u`.
- The printer (`format`) lays out `match` and `catch` by one rule: each case body starts on the line after `=>`, and a blank line separates the cases unless there are at most two and each has a head and one line of body (`case_chain` of `ulang/format.u`); a `list(…)`, `set(…)`, `map(…)`, or `array(…)` wider than 80 characters has one element per line, and so has a procedure head that is wider, with the modes `in`, `out`, and `ref` in front of the first formal of their group.
